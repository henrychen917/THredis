## 1. Double text — FIXED, not accepted

The residual was described as "last-digit artefacts of the shortest-representation algorithm". That
framing understates it: `1e126` printed as `1e+126` here and `9.999999999999999e+125` there — a
6-byte reply against a 22-byte one. It is not a last-digit difference, it is a different answer.

**Redis renders every double through Grisu2** (Loitsch, *Printing Floating-Point Numbers Quickly and
Accurately with Integers*, PLDI 2010). Grisu2's digits always round-trip but are **not always the
shortest**, and `std::to_chars` always gives the shortest. They disagree for roughly one double in
700. Matching means generating Grisu2's digits, which is an ordinary published algorithm, not an
artefact to be approximated:

* `src/base/numeric.h` now carries `grisu2_digits()`, written from the published description and
  from the 7.4 binary's observed output. The cached powers-of-ten table is **generated by exact
  rational arithmetic** (`f = round(10^k / 2^e)`, `f` in `[2^63, 2^64)`, 87 rows from 1e-348 in
  steps of 8), not transcribed from anywhere.
* One detail is load-bearing and is called out in the code: the row spacing is ~26.6 binary
  exponents and the acceptance window is 29 wide, so for some exponents **two adjacent rows both
  qualify** and the starting index of the scan decides which one is used — which decides the last
  digit. The starting index truncates *before* the offset is added.
* The fixed/scientific rendering rule and the `|v| <= 2^62` integral fast path were already right
  (F7 of the sibling lane); they moved into the same file so the parsers sit beside the formatter.
* `resp.h` and `resp3.h` keep only their framing. RESP2 bulk and RESP3 `,` share one call, because
  redis renders both from one `d2string`.

Validation is the point of this change, so it was over-provisioned: the 12 887-value corpus reaches
0 in RESP2 and RESP3, and a further **950 000 values** (every exponent × seven mantissa shapes,
every power of two from 2^-1074 to 2^1023, `m × 10^e` grids, 750 000 random bit patterns, random
integral doubles, and neighbourhoods of the 1e15…1e23 and 2^62 cutovers) are byte-identical.

Examples that move:

| value | before | after == oracle |
|---|---|---|
| `1e126` | `1e+126` | `9.999999999999999e+125` |
| `1000000000000000.2` | `1000000000000000.2` | `1000000000000000.3` |
| `7.18288826277728e18` | `7182888262777280000` | `7182888262777281000` |
| `9474039721387.188` | `9474039721387.188` | `9474039721387.187` |
| `-1.1919455290949598e-37` | `-1.1919455290949598e-37` | `-1.1919455290949599e-37` |

**Cost.** The formatter is off the GET/SET path — it runs once per score-shaped reply. Grisu2 is a
64×64 multiply plus at most 18 divisions; `to_chars` was doing more work in `chars_format::scientific`
plus a re-parse of its own output to recover the exponent, which this version no longer needs.
No knob: redis has none, and a parity server with a switch for "be wrong on purpose" is worse than
one without.

## 2. Numeric acceptance — the strictness was NOT deliberate

`NOTES-EDGEPROTO.md` S3 says "Documented as a deliberate divergence". That sentence is inside its
`## Shelved — reproduced, deliberately not fixed here` section, i.e. it records a **deferral**. The
brief asked for this to be verified rather than assumed, so it was:

* **No other record exists.** Nothing in the other 58 `NOTES-*.md`, in `docs/`, in `DESIGN-*.md`,
  in `tomokv.conf`, or in any code comment at any float parse site
  (`t_zset.cc:149`, `geo.cc:68`, `xshard_commands.inc:61`/`:397`, `blocking.inc:123`,
  `t_server.cc:826`) states decimal-only parsing as a decision. All were bare
  `std::from_chars(..., chars_format::general)` with no rationale.
* `NOTES-ZSET.md` gives the score-bound grammar and says only "Parsing consumes the whole argument
  and rejects NaN" — silent on hex, whitespace, empty and overflow.
* `NOTES-EDGEPROTO.md` F3 *is* a deliberate-strictness record, but it scopes itself to **integers**
  (`string2ll`) and never mentions doubles.
* `git log -S` over `parse_double_value` / `parse_score_range` finds no commit message that explains
  the choice.
* The decisive evidence is internal inconsistency: `INCRBYFLOAT k 0x10` **already** accepted hex
  (its parser is `strtold`-based), while `ZADD z 0x10 m` refused it. A policy that half the tree
  disobeys is not a policy.

So it was aligned. Redis does not have one float grammar; it has three, and this tree collapsed
them into one:

| grammar | redis routine | used by | accepts | refuses |
|---|---|---|---|---|
| **VALUE** | `getDoubleFromObject` → `string2d` | ZADD/ZINCRBY score, ZADD GT/LT/INCR, `WEIGHTS`, GEO lon/lat/radius/width/height | `0x10`, `0x1p-2`, `+5`, `05`, `.5`, `5.`, `5e-324`, `inf`, `infinity`, `INF` | `""`, leading space, trailing text, embedded NUL, `1e309`, `1e-400`, NaN |
| **BOUND** | `zslParseRange` → bare `strtod` | ZRANGEBYSCORE, ZREVRANGEBYSCORE, ZCOUNT, ZRANGE BYSCORE, ZRANGESTORE BYSCORE, ZREMRANGEBYSCORE | everything above **plus** `""`→0, `" 5"`, any leading whitespace, `1e309`→+inf, `1e-400`→0, `5\0 5`→5, and `(` alone as an exclusive zero | NaN, trailing text, a space *before* the `(` |
| **LONG DOUBLE** | `string2ld` | INCRBYFLOAT, HINCRBYFLOAT, every blocking timeout | as VALUE, one width up | as VALUE |

and numeric `SORT` is the BOUND grammar plus `sortCommand`'s extra `errno == ERANGE` test, which is
why a subnormal is a perfectly good *score* and not a sortable *element*.

`src/base/numeric.h` holds all four (`parse_double_strict`, `parse_double_lenient`,
`parse_double_sortable`, `parse_long_double_strict`) plus `parse_timeout_ms`. The two duplicate
`string2ld` copies in `t_string.cc` and `t_hash.cc` collapse into it. Arguments longer than the
255-byte stack buffer fall back to a heap copy, because redis really does parse a 5000-character
number (`ZADD z 1.000…0001 m` with 5003 bytes is accepted there, and now here).

### What changed, each reproduced on a running server before and after

| command | before | after == oracle |
|---|---|---|
| `ZCOUNT z "" +inf` | `ERR min or max is not a float` | counts every score ≥ 0 |
| `ZCOUNT z "(" +inf` | same error | exclusive zero |
| `ZRANGEBYSCORE z " 5" +inf` | same error | parses as 5 |
| `ZCOUNT z 1e309 +inf` | same error | `+inf`, so `:0` |
| `ZCOUNT z 1e-400 +inf` | same error | `0` |
| `ZCOUNT z "5\0 5" +inf` | same error | `5` (the C string ends at the NUL there too) |
| `ZADD z 0x10 m` | `ERR value is not a valid float` | score 16 |
| `ZADD z 0x1p-2 m` | same error | score 0.25 |
| `ZINCRBY z 0x10 m` | same error | increments by 16 |
| `GEOADD g 0x10 0 m` | same error | longitude 16 |
| `GEOSEARCH … BYRADIUS 0x10 km` | `ERR need numeric radius` | radius 16 km |
| `ZUNIONSTORE d 1 z WEIGHTS 0x10` | `ERR weight value is not a float` | weight 16 |
| `BLPOP k +5` / `0x10` / `0x1p-2` / `1e-400` | `ERR timeout is not a float or out of range` | accepted |
| `BLPOP k inf` / `infinity` / `1e309` | same error | `ERR timeout is out of range` |
| `BLPOP k -inf` / `-1e309` | same error | `ERR timeout is negative` |
| `BLPOP k -0.0004` | `ERR timeout is negative` | a zero timeout: no deadline at all |
| `SORT` over a list holding `""` | `ERR One or more scores can't be converted into double` | sorts it as zero |
| `SORT` over a list holding `" 5"` / `0x10` / `5\0 5` | same error | sorts as 5 / 16 / 5 |
| `SORT` over a list holding `5e-324` | sorted it | `ERR One or more scores can't be converted into double` |
| `DEBUG SLEEP abc` | `ERR value is not a valid float` | `+OK`, sleeps zero |

Two details in the timeout path were **measured, not assumed**, and both are visible to a client:

* the seconds are scaled to milliseconds and rounded **up**, so any positive timeout however small
  is at least one millisecond — `BLPOP k 1e-9` answers a null after a tick. A truncating conversion
  (which is what the first attempt at this change did) makes it wait forever instead, and the
  battery's section 8 catches exactly that;
* the sign is then read off the **milliseconds**, so `-0.0004` s is `ceil(-0.4) = -0` — a zero
  timeout, not a negative one — while `-0.5` s is `-500` ms and is negative. Both were confirmed by
  timing an actual `BLPOP` against an empty key on both servers.

Sites touched: `t_zset.cc` (`parse_score_arg`, `parse_score_range`), `xshard_commands.inc`
(`parse_weight`, `parse_image_score_range`, `sort_number`), `geo.cc` (`parse_double`),
`blocking.inc` + `multi.inc` (one shared `blocking_reply_timeout_error`), `t_string.cc` and
`t_hash.cc` (`parse_long_double`), `t_server.cc` (`DEBUG SLEEP`). Nothing in the MVCC resolver, the
scatter engine core, or the single-owner rule.

## Deliberately still different, with the reason

| # | case | redis 7.4 | here | why |
|---|---|---|---|---|
| D1 | numeric `SORT` after an ERANGE in the **same pipeline batch** | `ERR One or more scores can't be converted into double` | sorts normally | `sortCommand` reads `errno` without clearing it. A leak, not a rule — see the reproducer below. |
| D2 | `DEBUG SLEEP 90000` | `+OK` after 25 hours | `ERR value is not a valid float` | redis has no upper bound and will hold its whole server. The 86 400 s cap is ours and predates this lane. Every *parse* difference under `DEBUG SLEEP` is closed. |
| D3 | `DEBUG <unknown-subcommand>` text | `unknown subcommand or wrong number of arguments for 'JMAP'. Try DEBUG HELP.` | `unknown subcommand or wrong number of arguments for 'debug' command` | the `container\|subcommand` naming item, `NOTES-EDGEPROTO.md` S1. Not a float. |

### D1 in full — the reproducer, and why it is not copied

`sortCommand` does `strtod(...); if (eptr[0] || errno == ERANGE || isnan(...))` and never sets
`errno = 0` first. Anything earlier that made `strtod` raise `ERANGE` therefore decides the answer
of the next numeric `SORT`. Reproduced by pipelining a **single** preceding command:

```
DEL q ; ZADD zr 1 a ; RPUSH q "5\0 5" 2 1 ; <one command> ; SORT q          (one TCP write)

  <one command>                         oracle SORT                                     here
  (none)                                *3  1  2  5\x005                                same
  ZADD zr 5e-324 x        (SUCCEEDS!)   -ERR One or more scores can't be converted…      *3 1 2 5\x005
  ZADD zr 1e309 x                       -ERR …                                           *3 1 2 5\x005
  ZADD zr 1e-400 x                      -ERR …                                           *3 1 2 5\x005
  ZCOUNT zr 1e309 +inf                  -ERR …                                           *3 1 2 5\x005
  ZINTER 1 zr WEIGHTS 1e-400            -ERR …                                           *3 1 2 5\x005
  GEOADD zg 1e-400 0 x                  -ERR …                                           *3 1 2 5\x005
  INCRBYFLOAT sf 1e-400                 *3  1  2  5\x005                                 same
```

The `ZADD zr 5e-324 x` row is the one that settles it: that command **succeeds** on redis and still
poisons the `SORT` after it. Unpipelined the leak disappears, because the event loop's own failing
syscalls overwrite `errno` between commands — which is also why an isolated probe of any of these
shows agreement. A behaviour that depends on whether the client happened to pipeline is not one a
client can rely on, so it is not reproduced. `tests/differ.py … doubles` therefore carries the
numeric-SORT *grammar* only through the directed battery (one request per reply), with the reason
written into the generator.

## Found on the way — handed on, not fixed here

### H1 — `SORT … ALPHA` orders by locale on redis and by bytes here

```
RPUSH q -3 1 abc " 5" +5 05 2
SORT q ALPHA     redis: 05 1 2 -3 " 5" +5 abc
                 here:  " 5" +5 -3 05 1 2 abc      <- byte order
```

Redis calls `setlocale(LC_COLLATE,"")` and compares with `strcoll`, so under this box's
`en_US.UTF-8` its order ignores punctuation and spaces at the primary level. **Pre-existing**:
identical on the base binary and on this branch, and it is a collation question, not a float one.
Its own lane; excluded from the differ generator with the reason written in.

### H2 — a cross-shard store's destination can be read stale on a long pipeline

Not a float issue at all, but this lane's instrument is what surfaced it, so here it is with a
recipe. On a **long pipelined stream**, a `ZRANGESTORE` that answers `:1` can be followed two ops
later by a `ZRANGE` of its destination that answers `*0`, while an *earlier* read of the same
destination answered with the content the later store was going to produce:

```
op 3228  ZINTERSTORE db:d5 2 db:r db:z2 WEIGHTS 5e-324 " 5" …   both: -ERR weight value is not a float
op 3229  ZRANGE db:d5 0 -1 WITHSCORES     here: *2 d 16      oracle: *0
op 3230  DEL db:d5                        here: :1           oracle: :0
op 3247  ZRANGESTORE db:d5 db:r (5 +inf BYSCORE   both: :1
op 3248  ZRANGE db:d5 0 -1 WITHSCORES     here: *0           oracle: *2 d 16
op 3249  DEL db:d5                        here: :0           oracle: :1
```

Reproducer (instruments in the lane scratchpad, not committed):

```
python3 window.py 101 3100 3260 40 <target_port> <oracle_port>     # 6404 ops in one write
  -> 140-156 diffs, 3/3 runs, on an affected server instance
python3 opbisect.py 101 <target> <oracle> 3260 3100                # ~60-75% per run
```

Properties measured:

* **boot-dependent.** One 16-shard instance reproduced 3/3 and ~75% of single runs; a freshly booted
  instance of the *same binary with the same flags* reproduced 0/6, and so did `--shards 1`. Routing
  is seeded per boot, so which shard pair a destination lands on decides exposure.
* **not table growth.** Inflating a fresh instance to 400 000 members and flushing did not arm it.
* **not the new grammar.** The changed code is argument parsing and double text: no state, no
  dispatch, no ordering. What the change does is let cross-shard stores that were previously
  *rejected at the parser* actually execute, which is how the stream reached the path at all.
* the smallest form seen was ~1800 ops of `GEOSEARCHSTORE`(error) + `ZRANGESTORE`/`ZRANGE`/`DEL`,
  but it is a race and that form did not reproduce on demand.

It belongs to the scatter engine, which the brief puts out of bounds for this lane, so the code is
untouched. **`tests/differ.py … doubles` is built not to depend on it**: every store in the stream
gets a unique destination that is never read back and never deleted, so the arm's evidence is the
store's own reply (a count, or the exact error) and nothing races. The destination *contents* are
still compared, deterministically, by the unpipelined corpus prober and by `tests/doubles.py`.

## Tests

* **`tests/doubles.py HOST PORT`** — 201 checks in nine sections: the Grisu2 values, the rendering
  rule and its cutovers, the VALUE grammar, the BOUND grammar, the long-double grammar, GEO, numeric
  SORT, the timeout grammar, the sub-millisecond timeout behaviour, and RESP3. Every rejection sits
  next to an accepted spelling of the same argument, and every rejection that could have written
  something is followed by a read proving it wrote nothing, so an over-tight parser and an over-loose
  one both turn it red. **It passes unchanged against the 7.4 oracle**, which is what makes it a
  parity battery rather than a transcript.
* **`tests/differ.py … doubles [seed] [-3]`** — 5000 ops over every double-taking argument, in every
  spelling both servers accept and every spelling both refuse. Two things are excluded on purpose,
  each with the measurement behind it written into the generator: numeric SORT (D1) and
  `SORT … ALPHA` (H1). Store destinations are unique and unread (H2). Coordinate spellings go to
  their own key and are read back by score, because equal-distance geo matches have no defined order
  on either server.

## Instruments (lane scratchpad, not committed)

`corpus.py` is the discovery engine rather than the differ: it sends each case to both servers with
an `ECHO` sentinel interleaved, so a command that answers twice — or not at all — is caught as a
desync instead of silently shifting every later comparison, and it reads back the stored value or
the surviving members after every probe. `dtoa_probe.cc` links `src/base/numeric.h` into a
standalone filter so the formatter can be swept against the oracle at 250 000 values a run without
rebuilding the server. `ask.py` sends one command per connection, which is how the D1 errno leak was
separated from a real grammar difference. `window.py` / `opbisect.py` are the H2 reducers.

## Inherited draft

Branch `deprecated/t-doubles` carried a 305-line `tests/doubles.py` and a differ generator from an
attempt that was cut off. Its 12 887-value corpus reconstruction was sound and is reused. Its
assertions were not: they froze the *old* behaviour as correct — asserting `1e+126`, asserting that
`ZADD z 0x10 m` must fail, asserting that `ZRANGEBYSCORE z " 5"` must fail — and its comments
described that behaviour as "deliberate", a claim the NOTES do not support. None of that survives.

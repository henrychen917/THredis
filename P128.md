p128 with 8 conns/thread is the FASTEST cell. Depth is not the variable; `conns/thread x
min(depth, ROB window)` is, and the threshold is the lane capacity:

    kRobWindow = 64            (max in-flight ops per connection)
    kInboxSlots = 1024         (the armed local-read lane has exactly this many entries)
    lane pressure = conns_per_thread x min(p, 64)

    16 x 48  =  768 < 1024  -> never full         (p48 peak)
    16 x 64  = 1024         -> full at p64 exactly (cliff starts)
     8 x 128 =  512         -> never full         (c8 p128 = 10.34M)
    32 x 32  = 1024         -> full from p32      (c32)

The same arithmetic covers the connection-count collapse: 2048 conns on 32 threads = 64/thread,
64 x 32 = 2048 > 1024; 512 conns = 16/thread, 16 x 32 = 512 < 1024. Accept distribution is
uneven (9..25 conns/thread observed per run), so the threads over the mean cross first.

## 2. Mechanism (from the code, `src/core/io_loop.h` + `src/core/ex_loop.h`)

1. The armed parser appends each eligible read to the thread's local-read lane. When
   `local_read_lane_has_room()` is false the read is DEMOTED with
   `ReadLocalFallbackReason::LaneFull`: an ordinary owner task posted to the shard owner's inbox
   (7/8 of them cross-thread with 16 shards on 8 threads).
2. `drain_local_read_tail()` returns 0 whenever `notified_task_depth_capped(1) != 0`, i.e. when
   ANY owner task is pending in this thread's inbox — the fairlane rule that gives a busy remote
   producer service every rotation. In a pure-read workload the only owner tasks in existence are
   OTHER threads' lane-full demotions.
3. So a demotion on thread A suppresses the lane tail-drain on thread B; B's lane keeps a residue,
   fills sooner, demotes into A and the others; their tails stop draining. The interleaved path
   still drains 32 local reads per 32 owner tasks, so the lane drains slowly instead of fully,
   rotations grow to ~1000 ops, every connection sits at its ROB cap, and the lane is chronically
   full: positive feedback — a congestion collapse, which is why the cliff is sharp and why only
   ~2% of reads need to be demoted for a 28% loss. The demoted reads also block in-order
   retirement of the local reads behind them (p99 doubles at p64: 2.3 -> 4.1 ms).

### Hypotheses A-D against this

- (A) ROB window 64 < 128 in flight: TRUE but benign — `acquire()` returning null is plain flow
  control, and c8 p128 (also ROB-capped) is the best cell. The ROB cap is what BOUNDS lane
  pressure; widening it would move the cliff to 8 conns/thread at p128 (see section 6).
- (B) drain chunk 32 / interleave: the chunk size is not the problem; the tail-yield policy is the
  amplifier (step 2 above). A bigger chunk would not stop the loop from seeding itself.
- (C) prefetch-capture overrun: capture is per 32-op chunk inside `drain_local_reads_bounded`,
  independent of pipeline depth; keyspace hit rate stays 100%. Not it.
- (D) memtier's closed loop: not a generator limit (same generator drives 10.34M at p128 with 8
  conns/thread). Its role is only that at p >= 64 every connection is permanently at its ROB cap,
  so lane pressure is sustained rather than bursty (p96 and p128 behave alike).

### Rotation order (from `io_loop.h` run loop, `flush_ready`, `ex_loop.h fused_pass_impl`)

One fused rotation is: `for_each_cqe` (recv completions -> `parse_and_dispatch` -> lane) ->
`flush_ready` { PHASE 1: walk `active_`, re-arm recvs, RE-PARSE unconsumed frames (-> lane);
`fused_baseline_pass` (EX: EARLY 32-op lane drain, owner tasks interleaved 32:32 with lane chunks,
lane TAIL drain only if no owner task is pending); PHASE 2: serve/send }. So within a rotation the
fresh arrivals are parsed BEFORE the previously deferred frames, and the lane is drained once,
after both. A deferred connection stays in `active_` because the pass reports Progress with bytes
left at rpos (`more_input`), and the re-parse attempt counts as work, so the loop does not park
while a frame is deferred -- correct: nothing external would wake it, and the next EX pass drains
the lane. `on_cqe` ends with `mark_active_known(c)` unconditionally, so a deferral on the recv path
also lands the connection in the PHASE 1 walk.

## 3. Per-connection armed-state footprint (from the layout locks and `rob.h`)

| component | bytes | note |
|---|---|---|
| `Client` (incl. `Rob<64>` header 192, `ReadLocalPendingFilter` 32, two inline `SmallBuf<512>` wbufs) | 1,984 | locked |
| ROB Op slots: 8 chunks x 8 x `Op` 336 | 21,504 | materialized lazily per chunk on first touch; a p1 conn holds one chunk (2,688) |
| rbuf (`kRbufInitial`) | 16,384 | malloc; touched bytes = in-flight x ~40 B request |
| wbuf growth beyond the inline 512 | ~4,600 | 64 x 71 B GET replies per window |
| `ReadLocalRobState` sidecar (RYOW write ring 16 x 16 B + controls) | ~300 | allocated only once a write generation is live; absent in pure reads |
| per THREAD: local-read lane 1024 x (16 B entry + 1 B reason) | ~17,400 | not per connection |

Resident per fully pipelined armed connection: ~49 KB. Touched per rotation: ~1,984 + in-flight x
(336 + 40 + 71) B = ~30.6 KB at 64 in flight, ~16.3 KB at 32. Per thread that is ~490 KB at 16
conns x 64 (inside the 1 MB Zen4c L2, shared with the memtier SMT sibling here), ~1.04 MB at 64
conns x 32 (the 2048-connection geometry: L2 overflow), ~1.96 MB at 64 x 64. So the connection
count collapse has a candidate footprint component that the depth collapse does not: at 16
conns/thread the touched footprint is 490 KB whether p is 64 or 128. Section 5 separates the two
with L2-miss/op at fixed in-flight (512/thread) across 8..64 conns/thread.

## 4. SHIPPED: lane admission -- defer, never demote; pressure-gated fair share; no knob

Files: `src/core/io_loop.h` (parser gate chain), `src/core/ex_loop.h` (quota, pressure window,
per-rotation decay), `src/core/thread.h` (counters), `src/cmd/t_server.cc` (INFO). Prototype knob
`--read-local-lane-full 0|1|2` and its CONFIG GET entry and parser test are removed (knob
philosophy: prefer no knob; the threshold self-derives).

1. LANE FULL -> DEFER. When `local_read_lane_has_room(demand)` is false the armed parser leaves the
   frame at rpos and ends the connection's pass (`defer_lane_full++`). Nothing was published: the
   ROB slot is acquired but not published (same shape as the MGET admission fence), no lane entry,
   no pending bit, no owner slot. The read is re-parsed by a later pass of the SAME thread after
   its EX pass drained the lane, and still completes locally. The former path (demote to the shard
   owner as an ordinary task, `ReadLocalFallbackReason::LaneFull`) is unreachable from the parser;
   `read_local_fallback_lane_full` stays in INFO for continuity and is 0 by construction.
2. PRESSURE WINDOW. Any deferral (either kind) sets `Impl::lane_pressure =
   kReadLocalLanePressureRotations` (8); `fused_pass_impl` decrements it once per rotation. While it
   is non-zero the parser's per-pass bound is `quota = max(1, kInboxSlots / active_.size())`;
   otherwise `UINT32_MAX`. (`ExLoop::read_local_lane_quota(live)`, one predicted byte test per
   parse pass; the division runs only under pressure.) "Live connections x observed depth": live =
   the active set; observed depth = the deferrals themselves -- a rotation whose aggregate demand
   fit the lane arms nothing.
3. FAIR SHARE -> DEFER. A read on a connection with `rob.in_flight() >= quota` is deferred too
   (`defer_quota++`, re-arms the window). By construction the sum of admitted local reads stays
   within the lane, so the lane-full deferral -- whose victims are whichever connections the
   rotation parsed LAST (section 7) -- stops firing after at most one rotation per pressure
   episode, and every connection progresses every rotation. The compare is the one the prototype's
   arm 2 already paid, against a register; the batch-extension test carries the same term.
4. Cost in the steady state (lane never full): one byte load per parse pass, one popcount+compare
   per eligible read. Measured PRE/POST at 9 conns/thread x p32 saturated (section 9): instr/op
   2279/2280 vs 2274/2264 (+0.2..0.7%), throughput +0.9% / +4.7% (noise band).

Two corrections measured on the saturated 4-thread rig (section 9) BEFORE the final form:
- The window was first re-armed by the quota's own deferrals. At the lane boundary (33/thr x p32)
  that kept it armed forever: 1.07M quota deferrals in 20 s where the lane itself refused 98 reads
  (0.8% of ops re-parsed vs 0.00008%), p99 1.03 -> 1.43 ms. A signal the actuator produces cannot
  police the actuator (the Sweep-ABANDON law). Final: only a LANE-FULL deferral arms the window.
- The share was first measured as `rob.in_flight()`. That counts replies PHASE 2's bounded serve
  has not flushed yet, which hold no lane slot; at 2x lane the busiest thread fell to 416 ops per
  rotation (from ~1000) because connections were throttled for unflushed replies. Final: the share
  is `Rob::pending_read_local_count()` = popcount of the pending local-read slot bitmap = the lane
  slots the connection actually holds, zero again once the EX pass ran.

Invariants untouched: single-owner writes; reads never obstructed by writes (a deferred read waits
for its OWN thread's lane, not for any writer); RYOW per connection (frame order is preserved --
the deferred frame is consumed before anything behind it; `tests/read_local_lane.py` proves a SET
and GET behind 64 deferred GETs reply in order with the new value); in-order retirement; every
layout lock (Op=336, Client=1984, ThreadCtx=1408, Shard=1440; `ReadLocalStats` sits behind
`read_local_state_` and `Impl` behind `read_local_.impl`, both heap, so neither lock moves;
Config back to its pre-prototype body at 624). `--thread-mode 2s` has no lane and no arm: the
quota call is inside `if constexpr (Fused)`.

Why not the alternatives: widening `Rob<64>` moves the cliff (section 6); a bigger lane moves the
cliff to a larger connection count and costs L2 (17 KB per 1024 entries); an always-on static
quota binds at 17+ active deep-pipelining connections per thread even when the lane never fills
(the unsaturated 64-conns/thread cell in 5.2 ran -7% with 2.7M quota deferrals; unconfirmed, may
be drift, but the gating makes it moot); changing the fairlane TAIL-drain rule (the amplifier) is
the write-path lanes' territory and unnecessary once no capacity demotion exists in pure reads.

## 6. Design item: widening `Rob<64>` would not help here (do not)

`kRobWindow = 64` is the flow control that BOUNDS lane pressure (`conns x min(p, 64)`). The best
cell of the study (8 conns/thread, p128 = 10.34M) is ROB-capped at 64 in flight per connection;
the cap costs nothing measurable and is what keeps 8 x 128 down to 512 lane entries. A
`Rob<128>` would double lane pressure and move the cliff to 8 conns/thread at p128 (8 x 128 =
1024) — i.e. it would make this anomaly WORSE unless paired with policy 2 above, and then it buys
only fewer partial-window round trips for a connection that is already saturating its thread.
Cost if it were done anyway: `read_local_pending_slots_` / `read_local_owner_slots_` are one
uint64 each (`static_assert(Capacity <= 64)` in rob.h) so the footprint-free bitmaps become two
words each (+16 B in the locked 192 B header, or a layout change), `kExSchedBuckets` (= kRobWindow
x classes, asserted 192) doubles, and each pipelined connection materializes up to 16 Op chunks
(43 KB) instead of 8 (21.5 KB): +21.5 KB per connection, +2.7 MB per 128 connections. Recommend:
leave the window; the lever is admission policy, not window width.

## 7. Why pure deferral is not enough: the rotation order starves the deferred set

Rotation order (section 2): fresh arrivals (CQEs) are parsed before the previously deferred
frames (PHASE 1 re-parse), and the lane is drained once, after both. Under SUSTAINED demand above
the lane -- N connections x min(p, 64) > 1024 with the server saturated so every window is full at
every walk -- rotation k serves the connections whose arrivals filled the lane and defers the rest
(say 8 of 40 at p32: 40 x 32 = 1280 > 1024). Their replies go out in PHASE 2; the clients respond;
those same 32 connections' CQEs arrive first in rotation k+1 and fill the lane AGAIN before the 8
deferred connections are re-parsed. The deferred set is the same 8 connections every rotation:
hard starvation, structural not statistical, and it would show as p99.9/p99.99 in the ms->s range
for a fixed subset of connections while p50 stays flat. The fair-share quota removes it: 40 x 25 =
1000 <= 1024, no connection can take more than its share, the lane never fills, every connection
is admitted every rotation. It also bounds the one unfair rotation at the start of a pressure
episode (lane-full deferral arms the window; the next rotation is already fair). Throughput is
unchanged by the cap in the saturated regime: the rotation is the RTT, and 1024 ops per rotation
is the lane-bound either way.

### 7.1 Starvation check -- RESULT (s3i, section 9.3) and why it is structural

Measured at 2x the lane boundary: 63 connections per thread x p32 = 2016 nominal lane entries
against a 1024-entry lane, server saturated (busy 99.8%), loadgen on its own physical cores,
0/10 contaminated samples in every cell, two replicates with the arm order rotated.

| arm | p50 ms | p99 | p99.9 | p99.99 | p99.99 / p50 |
|---|---|---|---|---|---|
| PRE (demote) rep1 / rep2 | 1.871 / 1.874 | 3.012 / 2.879 | 3.88 / 3.81 | 5.78 / 4.44 | 3.1 / 2.4 |
| POST (defer + quota) rep1 / rep2 | 1.236 / 1.359 | 1.967 / 2.138 | 2.58 / 2.77 | 4.04 / 3.84 | 3.3 / 2.8 |

Every tail of the deferring arm sits BELOW the demoting arm's (p99 -35% / -26%, p99.9 -34% / -27%,
p99.99 -30% / -14%), and the SHAPE of the distribution is unchanged (p99.99/p50 3.3 vs 3.1) --
it is the same distribution shifted down, not a fast bulk with a stranded tail. Hard starvation of
a fixed subset would put p99.9 or p99.99 into the tens of ms while p50 stayed flat; nothing of the
kind appears. And the mechanism was exercised rather than dodged: in the same window POST deferred
0.022-0.025% of ops (0.001% lane-full + 0.021-0.024% quota) where PRE demoted 42.6% of them.

The argument that this is structural and not luck:

1. Under pressure the parser admits at most `quota = max(1, kInboxSlots / |active_|)` lane slots
   per connection, so the total admitted across a rotation is at most `|active_| x quota <=
   kInboxSlots`. The lane therefore CANNOT fill from quota-respecting admissions, and in a
   quota-bounded rotation no connection is refused for lane-full -- wherever in the walk it sits.
2. `quota >= 1` by construction, so every active connection is admitted at least one local read in
   every rotation of a pressure episode. Progress per connection per rotation is independent of
   walk position, which is exactly what the rotation-order starvation above threatened.
3. The unfair rotation is bounded to ONE. Only a real lane-full event arms the window, so the
   first rotation of an episode may still refuse the connections it parses last; that event arms
   the window and the next rotation is already fair.
4. The loop is policed by the lane, not by the actuator. The window decays one rotation at a time
   and is re-armed only by a lane-full event: if the quota is working the window lapses after
   `kReadLocalLanePressureRotations` and the cap lifts; if demand still exceeds the lane, the lane
   itself says so again. (Arming it from the quota's own deferrals is the Sweep-ABANDON violation
   measured in section 4.)
5. The cap costs no throughput in the regime where it binds: the rotation IS the round trip and
   1024 ops per rotation is the lane bound either way. Measured at 2x lane: POST runs 1010 ops per
   rotation against PRE's 532, and POST is +1.1..+2.2% over the no-quota arm rather than below it.

The one residual risk the bench cannot rule out is a connection whose share is 1 (more than 1024
active connections on a single thread) competing with 64-deep peers; there its floor is one read
per rotation rather than a proportional share. That geometry is 65k+ connections on the owner's
64-thread rig and is out of scope for this lane.

## 8. Directed test: `tests/read_local_lane.py` (gate row "read-local lane admission battery")

### 8.1 Why the row drives a CAP and not load

Oversubscribing the 1024-entry lane by traffic is a RATE RACE against the drain, and a test client
cannot win it: the fused thread empties its lane every rotation, far faster than one Python process
can fill it. The first version of this row tried to win it anyway and lost in three escalating ways
-- serial writes (fired 17 times on the armed boot, never on the cheaper unarmed one), then
parallel writers and connection doubling, which on the GATE's box produced
`read_local_defer_lane_full FAIL delta=0 after 3 escalation(s), 2048 conns, 48 rounds` while the
row's own geometry line reported 256 connections x 64 deep = 2624 frames. The frames existed; they
were never in flight together. A row that fires only on a saturated rig is not a gate row, and an
anti-vacuity row that cannot make its own precondition is the vacuity trap itself.

`DEBUG READ-LOCAL-LANE-CAP <n>` lowers the ADMISSION threshold only. The ring keeps its
kInboxSlots entries and its `& (kInboxSlots - 1)` masking, so a lower cap can never overrun it; it
moves only the point at which the parser stops admitting. A single connection pipelining more than
the cap in ONE write then oversubscribes the lane INSIDE ONE PARSE PASS, before any drain can run.
That removes the race completely: the row fires on any box at any speed, with 16 connections and
rounds that take 2 ms. 0 restores the derived value, which is what production always runs.

Cost, held to the bar the footprint defect in 9.5 set. `Impl::lane_admit_cap` is a uint16 at
offset 38, in the two padding bytes that already sat between `prefetch_capture` (37) and
`demote_context` (40): Impl does not grow, nothing moves, and it shares the first cache line with
`lane_head`/`lane_tail`/`lane_count`, which every admission test already reads -- so the admission
path gains one `movzwl` against a line it already owns and NO new line.
`Server::debug_read_local_lane_cap_` is a relaxed uint32 inside the existing contiguous block of
debug-only atomics that production never writes, so its line stays shared-clean in every core's L1;
each fused thread reads it ONCE PER ROTATION (never per op) and stores into the Impl only when the
value changes. Measured at the must-not-regress geometry (9.6): instr/op +0.32%, everything else
neutral.

### 8.2 What the row checks

On the B+ boot (`--thread-mode fused --atomic 1 --read-local 1 --read-local-atomic-filter 1
--enable-debug-command yes`), 16 connections, 6 rounds of DEPTH=64 shared GETs + SET own-key + GET
own-key in one write per connection, at lane cap 8:

| check | proves |
|---|---|
| order + RYOW across deferral | frame order and read-your-own-write survive a deferral: the SET behind 64 deferred GETs, and the GET behind it, reply in order with the new value |
| liveness | a deferred frame is re-parsed with no external wake (every round completes) |
| `defer_lane_full > 0` | the lane WAS oversubscribed -- without this every other check is vacuous |
| **capped > uncapped** | a CONTROL phase runs the identical traffic with the cap derived; the capped phase must produce strictly more deferrals, so the row proves the cap is why it fired instead of assuming it |
| `fallback_lane_full == 0` | capacity never creates a cross-thread owner task |
| `defer_quota > 0` | the pressure window armed and divided the lane |
| `read_local_hits >= 95%` | deferral does not cost locality |
| cap 0 restores the derived lane | the test hook leaves the production path unaltered |

Result on the gate's own boot (8 threads, 16 shards), `read_local_lane PASS (checks=8 skips=0
strict)`: `defer_lane_full` 92 against a derived-lane control of **0**, `defer_quota` 644,
`fallback_lane_full` 0, 6144 of 6144 shared GETs local (100.00%), slowest round 0.002 s. The same
row now also passes on the `--atomic 0` boot, which the load-driven version could never fire at

So no field this lane added landed on a hot line, and no hot field moved. The cost was not a
field at all -- it was an ARGUMENT:

```
read_local_quota = fused_executor_->read_local_lane_quota(active_.size());
```

C++ evaluates arguments eagerly, so `active_.size()` was loaded on **every parse pass** even though
the callee returns `UINT32_MAX` immediately on its `lane_pressure == 0` fast path. And
`IoLoop::active_` is at offset **7728**, i.e. cache line **7680-7743**, which it shares only with

(`notify_armed_` 7864 and `proto_max_bulk_len_` 7872, line 7808-7871 and 7872-7935;
`lb_controller_armed_` 2638). `active_.size()` is also the ONLY reference to `active_` anywhere in
the parse-and-dispatch function. So every parse pass pulled in one cache line it otherwise never
touched, with the mechanism dormant and every counter reading zero.

The arithmetic agrees with the fills. One cold line per parse pass, against ~2.9 ops per pass at
this geometry, is ~0.34 fills/op; the measured excess is +0.345 DRAM and +0.335 same-CCX per op.
At ~250 cycles for a DRAM fill and ~55 for a same-CCX fill that is ~105 cycles/op of exposed
latency against +72 cycles/op measured, i.e. the right size with some of it hidden by MLP.

#### Fix (commit 20d449a24): gate the argument, not just the answer

Test the pressure byte first and alone, and evaluate `active_.size()` only when the window is
actually armed. `lane_pressure` is on a line the pass already owns, so the gate itself touches
nothing new, and the steady state is back to one byte test per pass plus the per-op popcount
against a word the parser already writes. It is **semantically identical** -- the callee returned
`UINT32_MAX` in precisely the case now skipped -- so there is no behavioural change and no effect
on the 2x-lane result. Verification of the rebuilt binary (unit, batteries, both boots, differ) and
a re-measure of both rig cells are queued gated on quiet.done; the owner re-runs the two box cells.

# TomoKV control plane and consistency machinery

This document is derived from `src/` in this worktree. Source references use the line numbers present during this review. No server, benchmark, build, or gate was run. Repository design notes and other worktrees were not consulted.

## 1. Physical threads, roles, and owners

The stable identities are a dense thread ID, a connection, a routing bucket, and a `Shard`. A connection belongs to an IO thread; a shard belongs to an executor-capable thread. These ownership relations are independent. A thread owning a connection does not acquire write permission to that connection's keys.

`ThreadCtx` is a 1,408-byte object, with a one-byte atomic `Role` (`Idle=0`, `Ifid=1`, `Ex=2`), a separately published ready role, the active wake endpoint, client/shard pointer vectors, command counters, signals, and inbound transports. The maximum is 128 physical server threads. `Ifid` is the implementation's name for the combined receive/parse/dispatch/send role; there is no separate sender role (`src/core/thread.h:57`, `:303`, `:1131`).

| Mode | Running loops and ownership | Actual dispatch difference |
|---|---|---|
| `2s` / `split` (default) | Every selected physical thread has both an `IoLoop` and an `ExLoopT<false>`. Its current role selects the loop that runs. IO owns sockets, receive buffers, parsing, ROB allocation/retirement, scatter arenas, and writeback. EX owns execution of its shard vector, expiry, MVCC cleanup, blocking waiters, and owner-side persistence production. | Parsed owner work crosses a task lane; completion reaches the connection's IO through a ready bit or client channel. A role conversion returns from one loop, activates the already provisioned other loop, and runs it. |
| `1s` / `fused` | Every thread runs `IoLoop` with an `ExLoopT<true>` driven inside it. Both placement vectors (`ifid_threads`, `ex_threads`) contain every thread; the stored role is still `Ifid`. The IO loop owns the blocking wait and published wake endpoint. | The ordinary route still posts to the shard owner's task lane, including the self lane. Same-thread completion can call the IO completion callback directly. The optional local-read lane adds foreign-store reads under separate lifetime and ordering checks. |

The mode boundary is a boot-time template choice, not a branch that turns each command into a different kind of executor. Split allocates both loop arrays in `src/main.cc:336`, provisions the opposite role before serving (`:387`, `:521`), and selects the loop at `:424` and `:560`. Fused does the analogous allocation at `src/core/genthread.cc:88`, initializes on the pinned thread at `:122`, binds the executor into IO at `:165`, and starts serving only after the loaded/ready/running boot barrier. `Placement::build_fused` rewrites role labels to `Ifid` and duplicates the two thread views (`src/core/placement.h:37`). Fusion therefore changes scheduling and handoffs; it preserves single-owner writes.

Mode also selects short-reply representation. Fused ROB acquisition arms `Op::reply_code_ok_`; split leaves it zero. Eligible fixed replies and signed 32-bit integer replies can then store a one-byte `reply_code_` and `reply_ival_` instead of constructing RESP bytes on EX. Plaintext writeback formats the code into connection fill storage, reserving at most 16 bytes; paths requiring an ordinary reply buffer materialize it first. The shared writeback implementation contains both cases, but split operations never carry a code (`src/core/io_loop.h:4004`, `src/net/rob.h:197`, `src/exec/op.h:61`, `:340`, `src/net/wb.h:74`, `:349`).

Without explicit placement or ratio, split requests every allowed CPU, with `io = N - floor(N/2)` and `ex = floor(N/2)`; fused selects every allowed CPU for both duties. Placement rejects a total above 128 rather than resizing the channel mesh. The default 16 shards are assigned round-robin over executor thread IDs; accepted shard counts are 1–256. A physical executor-capable thread can own zero shards (`src/core/server.h:238`, `:364`, `src/core/placement.h:37`, `:73`, `src/core/config.h:1266`).

### The executor is a loop with explicit deferred debt

`ExLoopT` contains its own 1,024-entry control/persistence ring, cached time/configuration, cursors for expiry and version cleanup, and six task/release debt queues: `atomic_deferred_`, `multi_retries_`, `xshard_retries_`, `ordered_deferred_`, `stale_tasks_`, and `stale_releases_`. Its `WbEngine` remains allocated for statistics but never serves clients. Split `ExLoop` is locked to 6,112 bytes (`src/core/ex_loop.h:181`, `:213`, `:3327`, `:3369`, `:3425`).

An ordinary split pass services stale forwards and borrow returns first, then MULTI retries, atomic deferrals, and scatter retries. Fresh tasks wait while scatter retry debt or ordered deferrals remain. After execution it flushes pending group decisions, services blocking waiters on a 10 ms beat, and advances persistence/control work. A pass with no work counts as idle, spins with `pause` for a 2,048-pass budget, then performs an unmasked sweep and arms a kernel wait. Once a placement drain has been acknowledged, even expiry and config refresh must stop touching the shard vector (`src/core/ex_loop.h:701`, `:731`, `:759`, `:769`, `:800`).

The coarse geometry is 32 parsed operations per fused parse invocation, 32 operations per execution batch, and 16 connections per writeback service pass. Overlap variants change these quanta and stage order, described later; they do not create more physical thread roles (`src/core/genthread_pipeline.h:11`, `src/core/io_loop.h:6870`).

### What crosses a thread boundary

`Task` is 32 bytes: `Client*`, 64-bit ROB operation ID, signed shard override (`-1` means use `Op::shard`), optional low-32-bit enqueue timestamp, and optional `ScatterState*`. The receiver resolves the operation through the ROB rather than retaining a reusable `Op*`. A client cannot be destroyed until its ROB and wire references are quiescent (`src/core/thread.h:75`).

Each consumer has one first-touched task allocation of `nthreads * 1024` slots, subdivided into SPSC lanes. Each lane has separate 64-byte producer and consumer control lines. Split reserves 256 slots for each executor producer, then partitions the remaining capacity into power-of-two IO lanes. Fused assigns exactly 1,024 slots to every producer, including itself. Thus “1024 inbox slots” is not a global per-executor capacity, and a full producer lane can reject work while other lanes remain empty. Repartitioning requires every retired frontier to equal its producer tail; it happens at boot or the FLIP drain/install boundary, never during push/pop (`src/exec/masked_queue.h:51`, `:58`, `:102`, `:117`, `:170`).

The other three transport families retain one fixed 1,024-slot channel per producer: completed-client notices, `(shard, pointer)` borrow returns, and IO-to-IO `ClientTransfer` records. A task push publishes initialized bytes with a release tail store; ordinary SPSC publication needs no contended producer RMW. The notification mask does use atomic operations, amortized by batching. Ordinary dispatch leaves the frame at the parse cursor when enqueue fails, so it can be parsed again after capacity returns; scatter reserves its whole fanout before publication (`src/core/thread.h:96`, `:110`, `src/exec/exqueue.h:30`, `src/core/io_loop.h:5246`).

Masks select active producers; they are not the only correctness witness. The 100 µs signal sweep republishes task bits for nonempty lanes, and the pre-park path scans channels without the mask. Parking publishes blocked state and executes a sequentially consistent fence before checking inbound work. A producer wakes only on the relevant transition while the consumer is blocked. Prepared wake SQEs are submitted before another busy iteration; otherwise a queued wake could remain outside the kernel indefinitely (`src/core/thread.h:854`, `:896`, `:1006`, `:1088`, `src/core/io_loop.h:686`).

Runtime SIGINT/SIGTERM sets `Server::shutting_down_`, sets each published thread's stop flag, and rings the shutdown doorbell. These are outer-loop stop conditions, separate from placement-drain acknowledgements. The epoll park has a 50 ms ceiling so an idle loop rechecks stop even without a new connection. Main joins workers before releasing store-held MVCC references and reaping IO's deferred arenas; that final single-threaded lifetime cleanup must precede IO-pool destruction (`src/main.cc:63`, `:351`, `:594`, `src/core/ex_loop.h:705`, `src/core/io_loop.h:547`, `:724`).

## 2. Versions, decisions, and their lifetimes

### A version is a displaced object plus an external decision

There is no version chain in the key object. `FlatStore::atomic_pending_` points to a lazily allocated, 1,352-byte `AtomicPendingState`: a chronological doubly linked entry list, 64 connection-hash list heads, a live-entry count, script intents, and size-class entry/value freelists. `AtomicEntry` is a 144-byte header followed by `capacity` object pointers and, where needed, copied key bytes. It records the originating 64-bit connection ID, a 64-bit membership filter, a key span, and pointers to the group's epoch, abort flag, and lifetime references (`src/store/atomic_mvcc.h:18`, `:85`, `src/store/flatstore_atomic.inc:904`).

An owner installs a replacement into the ordinary hash table immediately and writes the displaced `KvObj*` into `entry.parked()[i]`. A deletion installs a null physical value. After the owner pass, it links the entry to the shard list and its connection bucket. The new candidate's decision belongs to that entry; its value is found in the **next matching entry's displaced pointer**, or in the physical table if it has no successor. The first matching entry's displaced pointer is the pre-chain base. This is a chronological log of physical exchanges, not a sorted chain of committed versions. Duplicate key occurrences remain occurrences and the last eligible one wins (`src/store/flatstore_atomic.inc:345`, `:388`, `:1005`, `:1131`).

For example, starting with physical `A`, installing group G's `B` leaves `G.parked=A, physical=B`; installing H's `C` leaves `G.parked=A, H.parked=B, physical=C`. G's candidate is now `H.parked`, not a value pointer stored in G. A group that aborts can therefore leave a physical candidate behind until cleanup without making that candidate visible to ordinary owner reads.

A command-wide group is an arena-resident `ScatterState`, not a `ShardGroup`. `ShardGroup` is only one touched shard's range in `key_order[]`. `ScatterState` owns the shared pending count, references, command kind, phase, origin connection, snapshot/expiry cuts, gathered results, and one isolated 64-byte decision line containing `atomic<uint64_t> epoch` and `atomic<bool> aborted`. Epoch zero means undecided/private; a nonzero epoch is a commit ticket. An aborted epoch-zero entry is decided-aborted, not unfinished. Ordinary pseudo-entries carry their own plain `epoch`; EXEC entries can have `group==nullptr` while still pointing to a transaction's shared decision (`src/cmd/scatter_engine.inc:80`, `:429`, `:590`, `src/store/atomic_mvcc.h:24`, `src/store/flatstore_atomic.inc:524`).

The allocation is normally one pending entry per touched shard per atomic group, with eight bytes per key occurrence for displaced pointers. DEL/UNLINK add packed key offsets/bytes rather than allocating empty value objects. The image-apply path constructs and admits the entire shard fragment before its exchange pass; atomic MSET constructs/adopts and admits each value inside its install loop and can abort after earlier exchanges. `atomic_prepare_capacity` uses the table's 70% growth/tombstone discipline; allocation failure or maxmemory refusal marks the group aborted. Already installed candidates remain hidden and are reclaimed later (`src/store/flatstore_atomic.inc:294`, `:395`, `src/cmd/atomics_glue.inc:159`, `:200`, `src/cmd/scatter_engine.inc:2670`).

### Choosing a value

The executing owner temporarily sets `FlatStore::atomic_read_epoch_` and `atomic_read_origin_conn_id_`. The resolver first probes the physical table, then walks the pending list in installation order. A `1ULL << (hash & 63)` membership bit rejects some entries; surviving entries require full hash and key-byte equality. It reconstructs each candidate from the next displacement as above (`src/store/flatstore_atomic.inc:278`, `:993`, `:1042`).

For each candidate, it skips an aborted group and a foreign epoch-zero group. A committed candidate is visible when its effective epoch is at most the read cut, or when it belongs to the reading connection. A same-connection private candidate outranks every committed candidate. Among committed candidates, the largest effective epoch wins; equal epochs favor the later occurrence. Before visibility/ranking, an epoch lower than the immediately preceding considered nonzero epoch is lifted to that epoch when both records have the same connection ID. The resolver and collapse both contain this program-order repair. A bare “choose max commit timestamp” description would omit behavior needed for RYOW (`src/store/flatstore_atomic.inc:1067`, `:1085`, `:1111`, `:1745`).

After choosing the object, the resolver applies its expiry deadline to the operation's cached clock. Cross-shard commands stamp one `now_cut_ms` in IO and install that same clock on every owner; the MVCC cut alone cannot prevent two fragments from straddling a TTL deadline (`src/store/flatstore_atomic.inc:1214`, `src/cmd/scatter_engine.inc:532`, `:1890`).

Ordinary tasks must be parked **before** entering a handler when an older undecided unit of the same connection matters. An EXEC's own unit includes both its parent epoch word and every child scatter epoch word; pointer equality with only the parent would deadlock it against its own child. `atomic_has_foreign_unit_undecided` searches the connection bucket and ignores foreign connections, its own unit, committed entries, and aborted entries (`src/store/flatstore_atomic.inc:233`, `src/cmd/multi.inc:218`). The executor's exact dispatch rules are described with transaction execution below.

### Drawing a ticket is not publishing a readable cut

`Server::commit_seq_` is a 64-bit ticket dispenser. `atomic_commit_safe_` is the separately published read watermark. A commit batch increments `atomic_commit_inflight_`, reserves consecutive tickets with one `commit_seq_.fetch_add`, release-stores tickets into all its decision words, then loads the drawn sequence **before** decrementing the inflight count. Only the decrement that observes one outstanding committer can CAS the safe watermark upward to that sampled sequence. If another committer is still between reservation and epoch publication, the safe watermark stays behind (`src/core/server.h:2560`, `:2576`, `:2587`, `:2619`).

There is no admission-order commit frontier. Install order and ticket order can differ. Successful standalone groups whose last owner has finished are linked into a thread-local intrusive commit list without allocating. At the executor boundary, one reserve/publish bracket assigns consecutive tickets to the list, then completes AOF/notification work, closes each apply window, release-stores `OpState::Done`, and notifies IO. The “last owner publishes” description therefore includes a delay until that owner's commit-batch flush (`src/cmd/scatter_engine.inc:3718`, `:3790`, `:3815`). Same-owner `atomic_commit()` closes its bracket before installing its local records; its justification is that no other task can run on those owned shards before the current task returns (`src/core/server.h:2610`).

### A read cut pins a representation, not the reply

`SnapshotCut` contains the inclusive 64-bit cut, slot index, registration bit, and atomic completion bit. Exactly one `ScatterArenaPool` per IO writes that IO's `Server::atomic_read_floors_` slot. It maintains a vector of unresolved cuts and a cached exact minimum/count. It publishes **cut + 1**, with `UINT64_MAX` meaning no constraint, then reloads the safe watermark and adopts a newer confirmed cut if publication raced a commit. This is one publish/confirm adjustment, not a retry-until-stable reader loop (`src/cmd/xshard.h:76`, `src/cmd/atomics_glue.inc:324`, `:349`).

Cleanup loads the safe commit cutoff first and the global minimum floor second. A prefix entry is eligible when aborted, or when its epoch is nonzero, strictly below the floor, and no greater than the earlier cutoff. The sequentially consistent registration/cutoff/floor operations make a cleanup that misses a new registration use an older cutoff. A physical snapshot freezes collapse entirely (`src/core/ex_loop.h:2022`, `src/core/server.h:2735`, `src/store/flatstore_atomic.inc:1491`).

At the last result-producing fragment, the command marks its cut complete and increments the IO completion counter. IO removes completed cuts before ordered reply retirement, so a slow earlier reply does not pin versions that no fragment will read again. Gathered borrowed values have their own borrow lifetime. Removing the last minimum rescans the unresolved vector; ordinary removals use swap/pop and update the moved slot (`src/cmd/scatter_engine.inc:3712`, `src/cmd/atomics_glue.inc:401`, `:430`). The usual unresolved-cut admission limit is **eight per IO**, enforced while atomic activity is present; read-only gaps can carry more, bounded by the participating ROBs. Cross-owner scripts use their own cut limit. A full window returns backpressure before posting (`src/cmd/xshard.h:117`, `src/cmd/scatter_engine.inc:1822`).

### When old versions die

Collapse consumes an eligible **prefix of the shard list**. An undecided/ineligible head retains later entries even if their keys are unrelated. Monotone, nonaborted installation/ticket order can discard predecessors directly. An inversion triggers membership and exact-key overlap checks; actual conflicting inversions or aborts build a temporary key table and compute the same winning version as the resolver, then splice it into the first retained successor or the physical table. The temporary table starts at eight slots and grows to a power of two covering twice the selected key occurrences. Retired pointers are sorted/deduplicated before freeing (`src/store/flatstore_atomic.inc:1495`, `:1510`, `:1703`, `:1848`).

The advertised cleanup “budget” is not a key/entry limit: `atomic_sweep` treats any nonzero budget as permission to collapse the whole eligible prefix and returns one. The executor's 64/256 budgets bound successful shard collapses, not work within one shard (`src/store/flatstore_atomic.inc:683`, `src/core/ex_loop.h:1975`, `:2722`). One collapse can walk and allocate in proportion to the retained list.

Each owner updates its own cache-line-separated `OwnerRecordRefs::nodes`; only its final node release decrements the shared state reference. A completion sentinel prevents an early-aborted entry from releasing the state before that owner's final task. `AtomicEntry::owner_refs` is a raw pointer into this owner-indexed array. Migration does not transfer that reference accounting; §5 describes the resulting shared-counter defect (`src/cmd/scatter_engine.inc:416`, `src/store/atomic_mvcc.h:28`). Reply retirement returns the admission credit and frees unneeded result contents; the arena itself stays until both record and WATCH references reach zero. Failure to allocate deferred-destruction bookkeeping intentionally leaks that arena rather than freeing live decision pointers (`src/cmd/scatter_engine.inc:3997`, `src/cmd/atomics_glue.inc:467`).

Entries are recycled by allocation class up to 4,096 cached entries and 4 MiB per store. Armed read-local objects additionally wait for their QSBR grace period before reuse; wire borrows can retain them beyond that. At shutdown, after workers join, fused first drains every local-read retirement FIFO and disables all stores' retirement hooks. Then every remaining epoch-zero group is marked aborted, collapse runs with unlimited cut/floor, and store-held group references are dropped before IO arena pools disappear. Disarming the hooks first prevents this unbounded final collapse from filling a FIFO whose readers can no longer publish another grace period (`src/store/flatstore_atomic.inc:927`, `:2269`, `src/core/genthread.cc:100`, `src/main.cc:352`).

### Admission credits are an independent window

`--atomic-window -1` resolves at boot to `min(16 * shards, 1024)`; zero is unlimited. Credits count admitted write groups through reply retirement, not installed records or commit tickets. `AtomicAdmissionLease` occupies a separate 64-byte-aligned thread-context block: IO privately owns `generation`, `available`, and `active`, and publishes `published_active` for CONFIG/INFO (`src/core/config.h:349`, `src/core/server.h:195`, `src/core/thread.h:65`).

Admission rejects a snapshot barrier or an odd credit generation, CAS-borrows up to **eight** credits from the shared pool if its private lease is empty, consumes one available credit, publishes active count, and rechecks mode/generation/barrier. A race rolls back admission. Exhaustion leaves the request pending before fanout. Returning the last active group also returns the unused lease batch so an idle IO does not keep credits from an active peer (`src/core/server.h:2449`, `:2460`, `:2517`, `:3210`).

CONFIG reconfiguration CASes the generation odd, waits for announced pool mutations, snapshots every IO's published active count into `reconfig_carry`, sets pool to `max(window-active,0)` and debt to `max(active-window,0)`, then publishes the next even generation. Old unused leases are discarded. Retiring an old-generation group pays debt before replenishing the pool; credit release spins while reconfiguration is odd. Turning atomic mode off stops optional new groups but existing activity and version lists remain live until drained (`src/core/server.h:2434`, `:3287`, `:3319`).

`apply_open` is a second, shorter lifetime: admission through the all-owner decision/abort edge. Physical snapshot coordination waits on this apply count, not admission leases, because an IO blocked inside SAVE cannot retire the replies that would return its leases. Confusing these counters creates a circular wait (`src/cmd/scatter_engine.inc:480`, `src/core/server.h:2772`).

### EXEC: shard command lists join one decision

`MultiSession` is connection-owned, allocated on demand, and stores copied argv strings, queue-error state, watched keys, and a prepared-but-unpublished EXEC. At EXEC, IO force-admits one group even with `atomic=0`, constructs `MultiExecState`, and lowers commands into per-shard ordered command-index lists with one cursor per shard. Each child has its own `Op`, completion counter, stage, per-shard done markers, and optional scatter state. The outer transport is a normal 32-byte `Task` whose scatter pointer has low bit one to tag `MultiExecState` (`src/cmd/multi.inc:8`, `:45`, `:101`, `:123`, `:1427`, `:1827`).

IO proves room for every outer shard task before publishing any. A full task lane or read-cut window retains the prepared EXEC and sets connection backpressure. It initializes owner-reference sentinels only on the final publication path, since a prepared request can outlive a shard migration. `exec_read_fanout` registers one shared cut through the **outer IO's** scatter pool when the transaction contains cross-shard MGET/EXISTS, a read scatter child with more than one shard group, or dereferencing SORT (including STORE). Its child pool must not overwrite that IO's floor. Other transactions register no MVCC cut. This test counts shards, despite its “multi-owner” comment; even several separate one-key reads in one EXEC do not themselves arm a shared cut. Every transaction nevertheless stamps one expiry clock, shared by all children (`src/cmd/multi.inc:664`, `:1551`, `:1574`, `:1627`).

On dispatch, the executor first forwards a stale shard route. A client-bearing MULTI fragment then checks (1) older same-connection parked tasks sharing a key, and (2) any undecided other unit of that connection on this shard. The second check is deliberately broader than key overlap. It parks in `atomic_deferred_` before executing a child. At install time, `prepare_write_key` only counts a violation of this condition; it does not introduce a mid-command ordering wait (`src/core/ex_loop.h:2777`, `:2816`, `:3075`, `src/cmd/multi.inc:876`).

Every fragment first joins the WATCH phase. Each watched key is validated/reserved on its owner under the transaction time cut; dirty WATCH state sets `watch_failed` and aborts execution. No command list proceeds until `watch_pending` reaches zero. Owner-side `watchers_` and `watch_reservations_` maps live inside `Shard`; reservation records retain the decision word and lifetime pin, so they remain meaningful when a group has installed no version (`src/core/shard.h:244`, `:493`, `src/cmd/multi.inc:1203`).

A watcher stores the client, its 64-bit WATCH generation, and the key's expiry deadline at arming. Validation treats a now-expired armed deadline as a change. A successful EXEC validation appends a reservation with `blocking=true`; ordinary atomic writers append `blocking=false` only where watchers exist. Finalization removes decided reservations, marks current watchers dirty for committed mutating reservations, and releases each reservation's shared reference. An undecided blocking reservation returns “not ready”; an undecided nonblocking mutator instead causes a validating EXEC to dirty/abort its WATCH without waiting. The matching logical token can pass its own reservation. Reservation allocation failure aborts that unit (`src/cmd/multi.inc:2169`, `:2230`, `:2261`, `:2307`, `:2316`).

**Two WATCH-validating EXECs can still form a wait cycle.** Let two connections WATCH `a,b` on different owners, then both EXEC read-only bodies. If owner A first validates transaction T and owner B first validates U, each installs its own blocking reservation. T's validation on B and U's validation on A both stop at `watch_finalize_reservation` before the nonblocking-mutator abort rule. Neither can finish the all-shard WATCH barrier, hence neither can decide/release the reservation the other needs. `service_multi_retries` keeps retrying without a validation timeout or priority rule. This path needs no intervening write or expiry (`src/cmd/multi.inc:1203`, `:2176`, `:2261`, `src/core/ex_loop.h:3025`).

Each shard advances only its own command-list cursor. A child touching several shards uses a command barrier; an owner that has done its stage returns `Retry` until the child finishes or publishes a new stage. Cross-shard child membership is captured into **four stages of four 64-bit masks**, covering 256 shards; the last old-stage participant rebuilds groups, writes the new immutable membership mask, then release-stores `stage`. Barrier-only fragments read that published mask, not the mutable scatter table (`src/cmd/multi.inc:45`, `:1911`, `:1959`).

Writes clone the latest visible value plus the transaction's own overlay, prepare a copied-key entry pointing to the transaction epoch, install the clone, and execute the handler against that private representation. Cross-shard read children use the transaction's registered cut plus the same-connection overlay. **Local children always set `UINT64_MAX`**, including GET and same-shard MGET, even if another child caused the transaction to register a cut. Disjoint shard lists progress independently; each local command is present only in its participating shard's list (`src/cmd/multi.inc:693`, `:921`, `:1010`, `:1055`, `:1076`, `:1902`).

Consequently EXEC supplies one write-group publication but not one read view across its commands. Start with `a=b=0` on different owners. A transaction containing `GET a; GET b` can read `a=0`, then a foreign atomic MSET/EXEC can commit `a=b=1`, then its other fragment can read `b=1`. It registers no cut, has no read-version reservation, and foreign clients are not dispatch-order dependencies. The returned pair `[0,1]` tears the foreign committed group. A cut registered for an additional cross-shard read does not fix its local GET children, which still pass `UINT64_MAX` (`src/cmd/multi.inc:664`, `:1055`, `src/core/ex_loop.h:2777`, `:3025`).

After finishing its list, each shard emits its AOF fragment once and decrements `lists_pending`. The final list claims `finalizer_claimed` by CAS. Success draws one ticket, publishes it to the parent and all child scatter epoch words inside the same safe-watermark bracket, and release-stores `finalized`. A child runtime error retains its own abort flag, so other queued commands can commit; a queue error gives EXECABORT, and a transaction-level failure aborts every child. Every outer task then finalizes reservations and releases its owner sentinel. The final `tasks_pending` decrement permits the public EXEC operation to become Done. IO assembles the command-order reply and returns the admission credit; state destruction still waits for retained version/WATCH references (`src/cmd/multi.inc:1289`, `:1997`, `:2035`, `:2048`).

### Cross-shard scripts add a private execution and certification machine

EVAL/FCALL with keys in multiple shards use another `ScatterState` phase machine even when `--atomic 0`. Zero/one-key and same-shard activations take the local route; disabling any of the stage-byte, workbench-byte, or cut-slot facilities retains the legacy route and its refusal when declared keys need different owners. The enabled scatter decision distinguishes shards, so two shards on one physical executor still use these waves (`src/cmd/scatter_engine.inc:1460`, `:1742`, `:1836`).

`Pin` installs an exact-key `AtomicScriptIntent` on every declared key, including absent keys: a malloc'd header plus copied key bytes on the store's singly linked intent list, with a 32-bit reference count for overlapping activations. No value/version is installed by a pin. Instead, `atomic_needs_version` and `begin_plain_version` force subsequent ordinary writes on that key to preserve their predecessor and draw a ticket. After all pins complete, the final participant chooses `script_cut = atomic_snapshot()`. `Read` serializes each declared value at that cut and the command's common expiry time into `ObjectImage` arrays. This costs a serialization and payload allocation per staged value, plus one relaxed shared byte-counter addition per fragment (`src/store/flatstore_atomic.inc:82`, `:129`, `src/cmd/atomics_glue.inc:10`, `src/cmd/scatter_engine.inc:2422`, `:3440`).

`Run` posts one task to the current owner of the first key's coordinator shard. That thread lazily retains a private `Shard` in `thread_local ScriptWorkbench`, outside `Server::shards()`. Each attempt clears its table, loads all staged images, executes the Lua handler synchronously, and serializes written keys into `state.apply`. One byte per declared key records read bit 1 and successful-write bit 2; Validate selects the read set, Apply the write set. A Lua command error does not erase earlier successful nested writes: the handler's reply and recorded write set both survive into Apply. The private store's object-byte limit is checked after loading and after Lua returns, so it is not a peak-allocation cap during Lua. Real-shard hit/miss statistics receive the private workbench's deltas (`src/cmd/scatter_engine.inc:2278`, `:2381`, `:2474`, `src/cmd/scripting.cc:394`, `:634`).

A read-only activation skips certification and tickets, unpins, and finishes at its read cut. A writing activation CAS-acquires the server-wide `script_certification_active_`, reserves an unpublished commit ticket, and posts Validate. This global flag serializes scripts' certification-through-Apply even for disjoint keys; ordinary writers never acquire it. Validation scans matching MVCC records and rejects any non-aborted epoch-zero record or committed epoch greater than `script_cut`. Losing certification or finding a conflict discards the reply/images/notification batch, advances the cut, and reruns Read/Run with pins still held. The default retry allowance is eight, giving at most nine attempts; exhaustion returns `TRYAGAIN Cross-shard script conflicted, retry` after unpinning (`src/core/server.h:210`, `:2721`, `src/store/flatstore_atomic.inc:155`, `src/cmd/scatter_engine.inc:3496`, `:3516`, `:3543`).

After successful validation, the implementation posts **Unpin before Apply**. Unpin decrements/frees the intents and rebuilds the group arrays; Apply initializes owner record references, installs the written images through ordinary atomic image-apply, then the final owner release-stores the reserved ticket into `state.epoch`, publishes the safe watermark, releases certification, and completes AOF/notification work. Every wave preflights all destination channels. A full channel retries publication without exposing a partial wave; `pending = task_completions + 1` includes a poster reference so a peer cannot rebuild the shared group arrays while the posting loop still uses them. Engine OOM aborts the group and closes any reserved ticket/certification state. Script cut-window exhaustion returns BUSY immediately, whereas ordinary atomic-credit exhaustion returns dispatch backpressure (`src/cmd/scatter_engine.inc:1822`, `:2289`, `:2337`, `:3410`, `:3569`, `:3596`).

**This phase order leaves a lost-update window.** Let a script stage `a=0`, run `INCR a` privately, and pass Validate; choose another declared key on a second shard so it uses scatter. After Unpin on `a` and before Apply on `a`, another connection's ordinary `INCR a` can read physical zero, write one, and reply one. With no earlier record or other pin on `a`, that write takes the unversioned path. Script Apply then installs its computed one, and the script also replies one. Final `a=1` cannot serialize two successful increments. Apply performs no script read-set revalidation, and the script certification flag excludes no plain writer. The comment that the reserved ticket orders every later writer after the activation does not cover a writer that observed the pre-activation value; after Unpin, that writer need not draw a ticket at all (`src/cmd/scatter_engine.inc:2526`, `:2538`, `:3569`, `src/cmd/atomics_glue.inc:122`, `:966`).

Auto stage budget is 4 MiB without maxmemory, otherwise `clamp(maxmemory / shards / 16, 4 MiB, 64 MiB)`; workbench budget is twice that and cut slots default to four per IO pool. Staging checks the sum of `sizeof(ObjectImage) + key length + payload bytes` after each owner serializes its fragment, so that cap is also checked after allocation. `script-crossshard-conflict-retries 0` allows the first attempt and disables retries; unlike the other three zero-valued knobs, it does **not** disable the facility. Lua's separate default instruction limit is 100,000, counted by a hook every 1,000 VM instructions; the hook fails on `instructions > limit`, so exact multiples get one extra hook interval. Zero maps to `UINT64_MAX`. The hook does not bound time spent inside a nested C++ command (`src/core/server.h:202`, `src/core/config.h:369`, `src/cmd/scatter_engine.inc:2464`, `src/cmd/scripting.cc:329`, `:1087`, `:1343`).

## 3. The local-read machine and the boundary of its guarantees

This lane exists only when `thread-mode=1s`, `overlap=0`, and `read-local=1`. Boot allocates one reader publication/statistics sidecar per thread, an extended pending-state allocation per shard, and a 1,024-entry local execution lane plus fallback array per fused executor. The baseline `ThreadCtx`, `Shard`, and `FlatStore` footprints stay fixed (`src/core/server.h:316`, `:582`, `src/core/ex_loop.h:196`).

Only GET/MGET are local candidates. Active MULTI/WATCH, blocked/subscriber state, conservative routes, pending own writes, and earlier owner operations can force the owner path. MGET also refuses key-miss notification mode. A GET miss goes to the owner; a stable MGET miss contributes nil locally. Typed or expiry-due objects demote the whole read so the owner performs the required lookup/expiry effects. Local replies copy bytes before the thread publishes quiescence; they do not retain a foreign raw pointer for the send (`src/core/io_loop.h:4398`, `src/core/ex_loop.h:1205`, `:1488`).

### RYOW follows connection generations

Pure-write connections initially record only the newest write's ROB ID. The first local read arms tracking; if pre-arming writes remain live, an arm fence forces owner reads until those writes retire. The first subsequently tracked write allocates `ReadLocalRobState`. Its 64-entry ring holds `(hash, op_id)` pairs, with 16-bit rejection tags and valid/wide/keyset bitmaps. A precise MSET of at most 16 keys uses one descriptor plus argv-based overlap checks; larger or unenumerable writes use a conservative overflow generation. Retired IDs are pruned lazily. Since every ring entry names a live ROB operation and the ROB has 64 slots, a new write cannot overflow a correctly maintained ring. Sidecar OOM falls back to the unarmed fence protocol (`src/net/rob.h:68`, `:81`, `:474`, `:661`, `:828`).

Already parsed local reads also have to precede younger conflicting owner work. IO stages a demotion plan and reserves the required owner task capacity before committing the change of route. The lane tracks worst-case demotion demand with a 1,023-task ceiling, reserving one task for the younger point command. A full local lane leaves input unconsumed; it does not silently turn pressure into owner dispatch. Lane-full events arm an eight-rotation pressure window; during it each connection's quota is `max(1, effective_lane_capacity / max(1, active_connections))`. Quota refusals do not rearm the window. The default interleave services 32 local reads, 32 owner tasks per captured producer, and further bounded local chunks, rather than draining all owner backlog before writeback (`src/core/ex_loop.h:49`, `:297`, `:335`, `:488`, `src/core/io_loop.h:4448`, `:4545`).

### Foreign visibility uses both a filter and sequence validation

The extended `ReadLocalStoreState` includes a 64-bit `probe_sequence`, owner mutation nesting/pending counts, retirement sink, and `ForeignReadSafety`. Sequence bit 0 means table mutation in progress; bit 1 is the pending hint; bits 2–63 are a generation. Closing the outer mutation bracket increments the generation; saturation permanently refuses local reads. Table resize/movement and atomic physical exchanges change this sequence; an ordinary immutable one-slot SET does not (`src/store/flatstore.h:555`, `:626`, `:3494`).

The foreign filter is **4,096 64-bit cells plus 4,096 32-bit touch epochs** per armed shard, not an exact key map. Each cell packs a 31-bit count, 32-bit fingerprint, and wildcard bit. A second fingerprint sharing an occupied cell makes it wildcard until the cell drains. Count saturation keeps it positive until a complete drain can rebuild; unenumerable mutations add one wildcard reference to every cell, and bookkeeping overflow poisons permanently. Owners publish a cell before advancing its epoch; readers acquire-load it. Prepared atomic entries publish the complete unsafe key span before physical changes and close it only when raw visibility is safe again (`src/store/foreign_read_safety.h:22`, `:65`, `:94`, `:195`, `src/store/flatstore_atomic.inc:1241`). “Exact per-key filter” in configuration comments overstates this mechanism.

A point probe samples the sequence, rejects a positive key filter or an odd/poisoned sequence, acquire-loads both table pointer/capacity/mask triples, and **rechecks the sequence before indexing**. It probes slots with acquire loads and compares full key bytes, then checks the sequence again. After copying the payload, `read_local_validate` checks it yet again. Pending-bit changes alone are ignored by the sequence comparison. With prefetch capture enabled, the exact key-verified object survives from prefetch to execute; execution does not reload a newer slot (`src/store/flatstore.h:914`, `:942`, `:3348`, `src/core/ex_loop.h:1502`).

MGET surrounds every value load/copy with a command-wide window. Up to 128 keys and with the atomic filter enabled, it records/rechecks per-key cell epochs; otherwise it records/rechecks touched-shard generations. It builds a private reply and clears it on a failed window. **Both MGET implementations make up to two attempts.** The noncaptured GET path makes up to three probe/copy attempts; default captured GET breaks on a topology/validation failure instead of recapturing. Failure then demotes to owner execution. These are per-operation sequence checks and reader retries in the default build of an enabled local-read lane; they conflict with the supplied “no reader retries and no seqlocks” law (`src/core/ex_loop.h:1015`, `:1028`, `:1054`, `:1170`, `:1299`, `:1450`).

### QSBR retires allocations at rotation boundaries

The read-local grace epoch is separate from the MVCC commit epoch. `ReadLocalThreadState::tick` publishes a rotation's quiescence with bit 63 denoting parked. The epoch and park/resume publications are sequentially consistent. Resuming first removes parked status while retaining the conservative old tick, then republishes the current epoch before probing. Grace scans ignore parked threads and require every active tick to be **strictly greater** than the retirement stamp; a remembered blocking participant is checked first (`src/core/thread.h:922`, `src/core/server.h:586`).

Each owner keeps a fixed FIFO of **4,096 32-byte retirement entries** `(callback owner, payload, auxiliary size, callback)`, with a 256-entry batch-stamp ring. Unlinks append without a global epoch RMW per object. The next seal advances the global epoch once and stamps the complete unsealed suffix with the returned old epoch. If stamp-ring capacity is full, the suffix merges into the newest batch under the newer stamp, delaying reuse. Reclaim scans participants once for the oldest batch and releases all batches below the resulting floor (`src/core/read_local.h:151`, `:277`, `:320`, `:378`, `:402`).

A full retirement ring makes the writer publish its own quiescence, repeatedly drain, execute `pause`, and call `sched_yield()` until a slot frees. There is no deadline or overflow allocation. A stalled active reader can therefore hold this owner inside reclamation indefinitely; in fused mode that physical thread also services connections. This is an explicit boundary to any unconditional non-obstruction claim (`src/core/read_local.h:299`, `:416`).

After grace, eligible raw/integer string blocks enter the owner's 48-class block cache, capped at 4,096 nodes per class and 768 KiB total, additionally limited on insertion by the contributing shard's current live object bytes. These blocks are excluded from logical/maxmemory usage. Borrowed payloads remain under the borrow registry instead. The queue/cache belong to the physical owner, so shard migration must drain old callbacks and rebind the store's sink before execution resumes (`src/store/kv_block_cache.h:62`, `src/store/flatstore_atomic.inc:1432`, `src/core/thread.h:980`).

The source-default SET representation remains immutable while this lane is armed. However, `TOMO_READ_LOCAL_SET_TAX_VARIANT=1` and `=3` are accepted build selectors for shard-sequence and per-object-sequence **in-place** overwrite. Selector 3 overlays a 32-bit raw-object sequence into the header and atomically copies mutable payload cells; sequence exhaustion falls back to replacement. Selector 2 is rejected because post-grace recycling became unconditional. The accepted overwrite builds explicitly violate the supplied in-place/sequence laws (`src/store/read_local_settax.h:17`, `src/store/kvobj.h:74`, `src/store/flatstore.h:2771`).

## 4. Scatter/gather: shard fragments, owner waves, ordered replies

### Preparing and publishing the first wave

IO enters scatter preparation only for command flags selecting multi-shard, all-shard, or configuration routing. The command-specific key grammar produces a key plan; up to 32 routes use stack storage, larger plans allocate temporary route storage. Each key is hashed once into `KeyRef {hash, arg, shard, stable_object, key_anchor}`. `key_order` groups original argument positions by shard; `ShardGroup {shard, begin, count, membership, scan_cursor, error, aux}` describes each span. Results remain indexed by original key position. The arena carves these arrays together; the atomic write/apply cases additionally have a shard-to-group lookup array and owner progress slots (`src/core/io_loop.h:4946`, `src/cmd/scatter_engine.inc:82`, `:93`, `:146`, `:772`, `:811`, `:1727`).

The shortcut named `same_owner` compares **shard IDs**, not physical owner IDs. Ordinary eligible commands whose keys all hit one shard become an ordinary local command. Different shards on the same executor still produce separate tasks and a scatter arena. Forced atomic children, dereferencing SORT, and selected command-specific cases bypass the shortcut. Read-fanout cut selection likewise uses more than one shard group, not more than one physical owner (`src/cmd/scatter_engine.inc:1742`, `:1798`).

Each participating shard gets one 32-byte `Task`, naming the same public ROB operation and `ScatterState` but a different explicit shard. IO counts the required slots in every destination owner's producer lane **before publishing any task**. Insufficient capacity destroys the unpublished preparation, leaves the input frame unconsumed, and retries later. Atomic waves publish each owner's shard tasks under one tail update, and preinitialize that owner's record sentinel before exposing any task. This saves tail publications; it does not collapse the tasks into one executor-major job (`src/core/io_loop.h:5009`, `:5063`, `:5107`, `src/cmd/scatter_engine.inc:1090`).

`initialize_owner_completion` counts groups per participating executor slot. For an atomic install wave, each owner-local `OwnerRecordRefs` has `remaining = group_count` and one lifetime sentinel in `nodes`; shared `record_refs` initially equals participating owners. Each shard record increments `nodes`. Only the final shard fragment on an owner removes that owner's sentinel and decrements shared wave `pending`; non-atomic waves decrement `pending` per shard. This converts one shared completion RMW per shard into one per owner for atomic installation. The record's plain `owner_refs` pointer remains relevant after the operation's reply (`src/cmd/scatter_engine.inc:1090`, `:1142`, `:1152`, `:3659`).

### One wave, multiple waves, and failed work

MGET gathers, and atomic MSET/MSETNX/DEL/UNLINK install, in the first owner wave. Atomic MSET's table capacity and entry are prepared first, but individual small values are allocated and admitted **inside** the install loop. Allocation or maxmemory failure can leave an installed prefix; the owner links that prefix's record, sets `aborted`, and relies on visibility selection and later collapse to remove it. MSETNX checks every local key against the pre-command view before exchanges, including duplicate-key handling, but another owner can still reject the group. This differs from the atomic image-apply path, which materializes its owner span before exchanges (`src/cmd/scatter_engine.inc:2665`, `:2700`, `:2738`, `:2789`, `src/cmd/atomics_glue.inc:159`).

Two-hop image commands first gather source objects into `ObjectImage` values, using type-specific snapshot serialization, including TTL and collection encoding. The last completing executor combines the images, builds destination groups, and posts the next wave **directly to executor task lanes**. SORT with actual BY/GET dereferences adds a source-image wave and a derived-key gather wave before possible store work. The ordinary two-hop/all-shard path requires the connection's older ROB operations to drain before publication and arms a parser barrier against younger work; one-wave MGET/MSET and the direct atomic rename path do not take that barrier (`src/cmd/scatter_engine.inc:282`, `:1216`, `:1264`, `:1872`, `:3675`, `src/core/io_loop.h:4990`).

Second-wave queue exhaustion is a terminal `FinalReply::QueueFull` error, unlike first-wave backpressure. Image conversion, table growth, admission, and allocation errors are recorded in shard result slots and selected by the finalizer. A pop whose phase-two winner disappeared can repeat selection up to eight times, then returns null unless queue failure supplied an error. Pending counters decide which executor becomes the finalizer; there is no separate coordinator thread for ordinary scatter (`src/cmd/scatter_engine.inc:1216`, `:1264`, `:3662`, `:3667`, `src/cmd/xshard_commands.inc:1845`).

Successful standalone atomic install/apply finalizers enter the executor's intrusive commit queue. The executor flush assigns ordered tickets and release-publishes group decisions, closes the apply lifetime, sets the public operation `Done`, and notifies its connection owner. Failed groups publish abort and finish without a successful epoch. Read cuts can complete as soon as the last future value dereference finishes, independently of when the public reply reaches the ROB head (`src/cmd/scatter_engine.inc:3711`, `:3743`, `:3790`, `:3815`).

### Gathering bytes and preserving reply order

Each MGET key has a `ValueSlot` with nil/inline/borrow kind, pointer, length, shard ID, and **1,024 inline bytes**. The payload is not zeroed at preparation. Integers and strings of length at most `min(shard.zc_min(), 1024)` are copied; longer payloads register a borrow on the owning store before the executor can run the next command. The borrow prevents overwrite/reuse until the IO release returns. Missing/non-string entries produce nil; key-order indexing preserves duplicate keys and input ordering (`src/cmd/scatter_engine.inc:56`, `:2847`).

IO assembles at ordered retirement. An all-inline MGET builds one ordinary reply. A borrowed MGET seals the current connection fill segment, disables coded replies for the rest of that operation, and alternates copied RESP headers, borrowed value segments, and static CRLF segments. Ownership of each borrow moves from the arena into the connection queue by setting its slot back to nil. TLS copies the borrowed bytes into its output and returns the borrow; EXEC's executor-side TLS child assembly retains descriptors for later IO retirement because it has no IO-to-owner release callback there (`src/cmd/xshard_commands.inc:1701`).

`Rob<64>` is the connection's reply-order mechanism. It can hold 64 issued operations and lazily allocates eight-operation chunks: 2,688 bytes per chunk, at most 21,504 bytes of `Op` storage beyond the 192-byte ROB header. Execution may set later slots `Done` first. `drain` acquire-loads from `flush` and stops at the first slot that is not `Done`, retires its reply and scatter state in sequence, then advances the released flush frontier. Completion notices are hints to inspect this ordered frontier, not permission to emit a later reply. `at(id)` only masks the slot number; it performs no generation check (`src/net/rob.h:140`, `:215`, `:737`, `:761`).

Borrow releases carry `(shard, pointer)` over their separate return channel and are forwarded if their remembered owner is stale. A full release channel keeps the release on IO's retry side; it cannot free the payload early. Scatter arenas can outlive reply retirement through atomic-record or WATCH references. Teardown first releases still-owned borrows, unregisters cuts, closes admission and script state, and defers arena destruction while references remain; the pool's allocation-failure fallback preserves lifetime by leaking rather than freeing a referenced arena (`src/cmd/scatter_engine.inc:2052`, `:3997`, `src/cmd/atomics_glue.inc:467`, `src/core/ex_loop.h:3143`, `src/core/io_loop.h:5528`).
## 5. Ownership transfer: stable stores, changing writers

### The physical unit and publication edge

`Router` has 16,384 atomic 32-bit bucket words, each packing a 16-bit physical shard ID and 16-bit executor ID. Boot divides buckets into fixed contiguous shard ranges; any remainder belongs to the final shard. Runtime changes only owner bits. A shard's tables, objects, expiry state, borrow registry, MVCC list, WATCH maps, and AOF producer stay in the same `Shard`/`FlatStore` allocation. A transfer changes which thread may mutate them, not their addresses or physical memory residence (`src/core/shard.h:548`, `:567`, `:658`).

The range API accepts only one or more **whole stores**. A partial shard range is rejected even though routing names individual buckets. It validates ownership and vector membership and reserves destination vector capacity before acquiring `Router::transfer_writer_`. `begin_transfer` is a try-lock: an existing writer, non-idle phase, invalid range, or wrong source rejects the move. Successful begin records range/source/destination and release-publishes `Preparing`, while bucket routes still name the source (`src/core/server.h:1997`, `src/core/shard.h:606`).

Under the globally quiesced ownership critical section, the mover adds shard pointers to the destination vector, removes them from the source vector, and rebinds each armed store's read-local retirement sink. Only then does `commit_transfer` release-store `Committed`, release-store each bucket's destination owner, and release-store the derived `Server::shard_owner_[sid]`. `finish_transfer` returns the descriptor to `Idle` and unlocks. The single-shard API requires capacity already reserved and uses swap/pop to remove source membership (`src/core/server.h:2040`, `:2054`, `src/core/shard.h:631`).

Runtime requests never read the transfer descriptor. They can enqueue against an old route. Before **any** shard access, including tagged EXEC and ownerless cleanup, `ExLoop::execute` compares the current `worker_of_shard` with its physical thread. A mismatch forwards the original task; channel refusal stores it in `stale_tasks_`. Borrow releases use the same rule and their own `stale_releases_`. FIFO retry stops at the first full destination and rechecks ownership on every attempt. The protocol pays an extra task handoff for a stale route instead of a per-request routing epoch/retry (`src/core/ex_loop.h:2777`, `:3115`).

### What the drain actually guarantees, and what it misses

`flip_quiesced` requires empty task/release inbound frontiers, stale queues, atomic/EXEC/scatter retry queues, ordered-deferred queues, pending commit/notify work, and snapshot backlogs; no active snapshot owner; zero global admission leases and apply windows; and no shard notification or recording-AOF output pending. Fused read-local additionally requires an empty local lane and **empty QSBR retirement ring**. Once acknowledged, frozen loops stop task, expiry, cleanup, waiter, and config walks until the controller releases the stage (`src/core/ex_loop.h:1794`, `:509`, `:731`, `:800`).

The read-local sink contains two owner-private destinations: callback context for the single-producer retire FIFO and a pointer to the unlocked block-cache free lists. Both are rebound by `adopt_read_local_retire_sink` before route publication; the source queue has drained, so no old callback remains to reach its cache after adoption. The negative-control macro `TOMO_RL_CACHE_NO_EAGER_ADOPT` deliberately removes this step. The ordinary build performs it at both transfer entry points (`src/core/server.h:1911`, `:1942`, `:2044`, `:2072`).

**Retained MVCC owner-reference counters do not satisfy that ownership rule.** `AtomicEntry::owner_refs` points to the original `ScatterState::owner_record_refs[executor_slot].nodes` or EXEC equivalent, a plain `uint32_t` shared by that owner's records across shards. The quiescence predicate checks admission/apply lifetimes, not `atomic_has_records()`, and frozen passes do not force record collapse. A decided group can retire its reply and leave records in two shards on one owner; moving just one shard preserves both pointers to the same counter. Subsequent cleanup on the old and new owners both execute `--*entry->owner_refs` without synchronization. Neither transfer function rewrites these pointers or splits their counts. This is a concrete data-race path across the ownership edge, affecting the shared group lifetime pin; zero admission does not prove zero retained records (`src/cmd/scatter_engine.inc:1090`, `:2673`, `src/cmd/multi.inc:934`, `src/store/flatstore_atomic.inc:1572`, `src/core/server.h:2765`, `src/core/ex_loop.h:1794`).

The keyless-notification sink also remains a plain pointer to an executor-local flag through the edge. Flip rebinds it at `ExInstall`; continuous LB rebinds it only at the end-of-pass `lb_control_pass` after resumption. That first resumed pass can execute or expire against the old flag. The forced notification sweep and forced post-adoption drain recover output, but they do not make a concurrent write to the old owner's plain flag legal. This does not meet the stated requirement that every owner-private structure named by a moved shard move in the same critical section (`src/core/shard.h:165`, `src/core/ex_loop.h:1833`, `:1854`, `:1922`).

`note_migration` updates `home_domain_` immediately to the destination domain and adds estimated bytes to statistics. No object copying, page migration, or cache-residency observation accompanies that update. Consequently `foreign_ops` compares execution against the most recently assigned domain, not an independently measured domain containing the working set (`src/core/shard.h:379`).

### Moving a connection is a separate ownership protocol

A connection transfer moves the existing `Client*`, unread input, ROB, and attached protocol state between IO owners. It requires an empty ROB, no prepared pipeline reference, no send/serve/completion claim, no WATCH references, barriers, admitted atomic groups, blocking command, MULTI session, or queued output. TLS is refused because its engine lives in the source IO's slot table; transient CLIENT/MONITOR/TRACKING or deferred out-of-band output can also refuse. Unread input is allowed. This is much stronger than `Rob::quiesced()` alone (`src/net/conn.h:720`, `src/core/io_loop.h:284`).

The destination reserves client/active/catalog/pubsub/tracking capacity and a writeback slot. The source reserves migration and forwarding records, removes the client from active/prepared work, and cancels the old io_uring receive; ownership remains at source until the kernel no longer holds the receive buffer. SQ starvation retries cancellation. Epoll instead duplicates the socket with `F_DUPFD_CLOEXEC`, reserves source rollback and destination registrations, and removes the original source registration. Before commit, failure restores catalog/routing state and re-arms source receive (`src/core/io_loop.h:322`, `:2545`, `:2575`, `:2750`).

Commit extracts the local catalog and pubsub/tracking routing, releases the source writeback slot, installs the `kWbMigrationInstalling` sentinel, removes source membership, updates the ROB's read-local statistics pointer, and publishes `Client::ifid_thread = destination` as the connection ownership edge. It updates the client directory and posts `ClientTransfer {client, catalog, routing, source}`. Destination drains this inbox before routed pubsub events, installs the reserved state and new writeback slot, and arms receive. A post failure after reserved capacity is an invariant abort, not a rollback across an ambiguous owner edge (`src/core/io_loop.h:2686`, `:2780`).

## 6. Continuous load balancing

### Signals and sampling cost

Key and client balancing default on. The shared defaults are sample rate 64, tick 1,000 ms, imbalance 25%, move cap 1, and cooldown 5,000 ms. **Any zero among these five shared controls disables both balancers**, even where that field would not otherwise be used by one side. Age sampling is a separate signal, default zero; it is not the continuous balancer's move criterion (`src/core/config.h:259`, `src/core/server.h:396`).

An executor keeps one countdown across visited keys. Every 64th visit increments the physical shard's bucket sample counter; a completed scatter fragment enumerates its touched hashes, so this measures key visits rather than commands or measured command service time. The controller folds unsigned 32-bit sample deltas multiplied by the sample rate into per-bucket EWMA weights, `new = 0.25 * sample + 0.75 * old`, with the first fold using the sample directly. Histories belong to immutable bucket IDs and survive migration. Every 10 ms an owner advances one owned shard's byte census by a 64-unit scan budget; byte totals are therefore asynchronous table-census observations, not instantaneous allocation counts (`src/core/ex_loop.h:2912`, `:3009`, `src/core/server.h:472`, `src/core/shard.h:337`).

Once per second, each IO enumerates its live clients and publishes `(connection ID, ROB dispatch ID, current in-flight depth)`. A client's new weight sample is `max(dispatch delta, in-flight depth)`; it uses the same 0.25 EWMA and is keyed by stable connection ID. The first observation includes all dispatches since that connection's zero baseline. The shared signal map is protected by `lb_signal_mu_`; owner totals are published as integer weights scaled by 1,024. Closed clients are erased. This signal does not measure socket bytes, TLS CPU, or parsing nanoseconds (`src/core/io_loop.h:7108`, `src/core/server.h:438`).

The fold also computes per-thread occupancy from busy/idle counter deltas, with the same EWMA. Continuous move selection below uses item weights and bytes, not that occupancy; flip's candidate selection can consult it. With controls disabled, per-request sampling is gated off and the corresponding signal arrays are not provisioned at boot (`src/core/server.h:492`, `src/core/ex_loop.h:186`).

### Exact decision and hysteresis

The cron writer computes `span = max(owner load) - min(owner load)` and `imbalance = 100 * span / mean(owner load)`; zero total yields zero imbalance. Key balancing considers the maximum of demand and byte imbalance. A streak increments, capped at three, only when imbalance is **greater than 25%**; it resets only below **20%**. At either boundary and throughout the intervening band it retains its value. Planning is admitted at streak three, so these need not be three uninterrupted hot observations if intervening observations remain in the band (`src/core/server.h:1141`).

A bucket carrying **strictly more than half** of total key weight suppresses the entire shard plan when demand imbalance is hot, and resets the key streak. The indivisible move unit remains a shard even though the dominant-unit test considers an individual bucket. This avoids repeatedly moving an unsplittable hot bucket, but also suppresses otherwise available byte balancing during that condition (`src/core/server.h:1182`, `:1219`).

For every unpinned item and every other destination, `weighted_lb_best_incremental_move` simulates moving its weight, bytes, and count. When demand is hot, a candidate must reduce demand span by more than `1e-9`; byte span is not a hard constraint. For a byte-only move, demand may increase by at most `1e-9` and byte span must fall by more than `1e-9`. Eligible candidates minimize resulting demand span, then byte span, then item-count span, then item ID and destination ID. **Continuous LB does not enforce equal shard/client counts**; count is a tie-breaker (`src/core/weighted_lb.h:50`).

The shard planner repeats this calculation up to `lb_move_cap`, updates its simulated loads, pins each chosen item, and stops once neither ratio is hot or no improving move exists. Any bucket still within its 5-second cooldown pins its whole shard. Client planning performs the same demand-only search once, yielding at most **one client per transaction regardless of move cap**. If both plans exist, the controller alternates preference. It consumes the chosen side's streak before starting the move (`src/core/server.h:1190`, `:1228`, `:1264`, `:1315`, `:1337`).

### Actuation and failure boundaries

`shape_transition_mu_` serializes admission against flip, snapshots, and loading. The planner checks that state before folding and again before publishing; an active LB transaction or flip/snapshot/load refuses the beat. Allocation failure increments capacity refusal. On admission it clears acknowledgements, increments the LB epoch, sets a 5-second deadline, and publishes either `ExDrain` for a shard plan or `ClientDrain` for one client (`src/core/server.h:1111`, `:1317`).

Shard balancing pauses new dispatch and waits for **every executor**, not just the two endpoints, to acknowledge the safe point. The coordinator then reserves all destination vector capacity, applies the transfers, stamps cooldown for every bucket in each moved shard, and releases `Idle`. Capacity failure releases the stage without a transfer; a transfer failing after validation aborts. Counters called `bucket_moves` and `bucket_cross_domain_moves` increment once per **shard** moved (`src/core/server.h:1362`, `src/core/io_loop.h:2901`).

Client balancing asks only the destination to reserve one slot, then the source waits for the chosen client to become movable. TLS, blocked state, or a MULTI-session pointer causes explicit refusal; ordinary live work can drain until timeout. `ClientMoving` begins before asynchronous receive cancellation and marks the cooldown immediately. Refusal and cancellation also consume cooldown, preventing repeatedly selecting an immovable heavy client. A 5-second timeout releases `ClientDrain`/`ExDrain`, but **does not cancel `ClientMoving`**: that phase remains until the asynchronous transfer commits or cancels. Wake SQ starvation retries the exact peer (`src/core/io_loop.h:2934`, `src/core/server.h:1395`, `:1444`, `src/core/ex_loop.h:1873`).

The full partitioner used by flip shares the weight/byte ordering but has a different invariant: each final target receives floor/ceil item count. It places pinned items first, sorts remaining items by descending demand, then bytes, then ID, and greedily selects least-loaded eligible targets with count/current-owner/ID tie-breaks. When the complete incumbent assignment satisfies count bounds and is no worse in both spans, it keeps it wholesale. This global incumbent check prevents a count-balanced no-op flip from reshuffling zero-weight items (`src/core/weighted_lb.h:131`).

## 7. Flip: learning a split, testing it, and changing roles

### Controller state and its observations

Automatic flip is split-only and defaults off. `Server` owns one `FlipController`, written by the main monitor under its cold mutex. Its phases are `Disabled`, `BootPending`, `Measuring`, `WaitingFlip`, `Seeking`, `Settling`, and `Anchored`. Enabled construction allocates per-thread fingerprint and work baselines and reserves a reading trail; disabled construction does not allocate those vectors. The beat is `lb_tick_ms`, or `max(1, nthreads)` milliseconds if that knob is zero. During an issued flip it polls at `max(1, tick_ms / 8)` to measure transition cost (`src/core/flipctl.h:257`, `:291`, `src/core/flipctl.cc:230`, `:1297`, `src/core/server.h:410`).

`ThreadCtx` embeds a `FlipFingerprintWriter`: two plain cumulative/partial windows, a work-window value, and a pass countdown. With `flip_work_window = W` (default 100), the first parse pass is sampled and subsequent sampled passes are uniformly 1 through `2W-1` passes apart, using IO's xorshift draw. Every dispatched frame in a sampled pass contributes; unsampled passes only decrement the countdown. `W=1` is exhaustive. Zero disables the writer, and all fused boots configure it dark. A sampled pass adds seven command-class counts, total commands, multikey key/operation counts, non-key argument bytes, and one depth bucket (1, 2–4, 5–16, or over 16 frames), then increments `closed_windows` (`src/core/flipctl.h:22`, `:38`, `:65`, `src/core/io_loop.h:5311`).

The classification uses the registry's legacy first/last/step key range, not scatter's command-specific key oracle. “Value bytes” means **all non-key argument bytes**, including numeric/options/script arguments. `AtomicGrouped` wins for any multi-key `MultiShard` command when boot `cfg.atomic` is set, including multikey reads; it does not ask whether this operation actually admitted an atomic group. Fingerprint fields are plain owner stores and the monitor copies the struct without a release/acquire snapshot protocol; checking `closed_windows` after that copy does not produce an atomic window (`src/core/io_loop.h:5330`, `src/core/flipctl.cc:297`).

The detector normalizes command-class counts, computes mean keys per multikey operation and mean non-key bytes per sampled command, then smooths each with weight 0.5. Its mix distance is

`D = [0.5 * sum(abs(class proportion differences)) + abs(key means difference)/(1+max(abs(key means))) + abs(byte means difference)/(1+max(abs(byte means)))] / 3`.

Pass-depth distance is retained for diagnostics and excluded from this trigger. The learned band is the maximum of twice pre-anchor jitter, `2/sqrt(max(sampled commands, 1))`, and the noise bound. A positive typed band substitutes its percentage for the first term, retaining the other floors; zero prevents mix triggering. The noise bound uses EW mean/variance and a decaying maximum, `max(peak, mean + 2*sqrt(variance))`, after at least two observations. Before anchoring it learns adjacent/learning-origin distance; afterwards it judges distance from the fixed anchor **first**, and learns only in-band observations (`src/core/flipctl.cc:51`, `:111`, `:153`, `src/core/flip_policy.h:287`).

Throughput is the delta of summed `ThreadCtx::total_commands_` divided by elapsed monitor milliseconds. Ordinary commands increment it on execution, scatter once at IO publication, and IO-local commands at IO execution; it is not a count of sent replies or executor fragments. A rate window resets if flip/LB is non-idle, snapshot/loading is active, or completed/refused flip and moved-client/shard counters changed. Otherwise every tick contributes to the long noise estimator. Its sample is the second relative difference `(r[t]-2*r[t-1]+r[t-2])/r[t-1]`; magnitude over 1 resets variance as a level change. Near-idle samples break the difference chain. EW time constant is `max(1, 30000/tick_ms)` ticks, with running-average warmup; reported sigma is RMS second difference, deliberately not divided by sqrt(6) (`src/core/thread.h:425`, `src/core/flipctl.cc:284`, `:339`, `src/core/flip_policy.h:247`).

A “stabilized” reading averages two adjacent tick rates when their relative distance, normalized by the larger magnitude, fits the typed/anchor/automatic band floored by twice long-window sigma. Automatic pair band is `2*max(pair distance, 1/rate)`. After acceptance, the second tick remains the first tick of the next pair: readings **overlap**. Anchored detection averages the pair without the stability rejection so a step can be detected. These are internal served-command observations; the controller cannot establish matched offered load (`src/core/flipctl.cc:334`, `:372`, `:395`).

### Boot, drift, and when a maneuver starts

Boot ignores rates at or below `nthreads * 1000/tick_ms` commands/s and resets its learning on such a tick. If fingerprinting is enabled, it also waits until at least one sampled work window appears. Non-idle deferral is capped at `ceil(30000/tick_ms)` ticks. Before that cap it uses a 0.5 rate EWMA, 0.5 EWMA of changes in normalized EWMA slope, and a five-position trend history. It starts when five-tick normalized slope is at most `2*max(slope-change jitter, (1000/tick_ms)/rate EWMA)/sqrt(5)` (`src/core/flipctl.cc:409`, `src/core/flipctl.h:521`).

At an anchor, mix shifts require consecutive out-of-band **sampled** observations; a tick without a fingerprint neither increments nor resets the streak. Rate surge/collapse requires consecutive pair means strictly above/below `anchor_rate * (1 +/- band)`. Both start with two confirmations. Pending rate evidence takes precedence over a simultaneous mix shift. In-band rate observations alone update anchor rate and jitter with alpha **1/64**; typed rate band stays typed, automatic rate band cannot fall below its settling floor. `flip_auto_band=0` disables these automatic change triggers, but does not disable the boot maneuver, forced trigger, controller vectors, or measurement machinery (`src/core/flipctl.cc:1221`, `:1272`).

Starting a maneuver records the current split, resets demand/origin/target windows and mix learning, and arms operation-age sampling at the explicit `lb_age_sample_rate`, or `nthreads` when it is zero. It sets the maximum model readings to `max(2, floor((30000/tick_ms)/2))`. That is a reading cap, not a wall-clock deadline; missing/unstable/transition-contaminated evidence can extend elapsed time indefinitely. Automatic mix/rate changes **cannot interrupt any active maneuver**. Only a forced trigger restarts it, waiting for an in-flight ownership transaction to finish first (`src/core/flipctl.cc:504`, `:1108`).

### Demand model, confidence interval, and exact move gate

For every stabilized reading, the monitor measures each physical thread's `work = max(0, wall_ns - max(0, idle_delta))`. IO share `f` is total IO work divided by total IO+EX work; each role must have positive observed operations and work. Busy counters are not the denominator. Role headroom is the minimum `idle_delta/wall_ns` among that role's threads. Both roles' headroom greater than the current verification band causes `hold-unsaturated`; a forced seek bypasses it. Unbooked scheduler time is counted as work by this formula (`src/core/flipctl.cc:690`, `:806`).

The Welford demand window needs at least two samples. Its interval is mean `+/- 2*sample_sd/sqrt(n)`, clamped inside `(0,1)` with `1e-9` endpoints. With one role unit per thread, or per SMT sibling pair, it evaluates every legal `s = 1..N-1` using `R(s,f) = min(s/f, (N-s)/(1-f))`. The candidate maximizes gain over the live split at the mean. Its pessimistic gain is the minimum at interval low, mean, and high; the optimistic bound is the maximum any split reaches at those three points. Move requires pessimistic gain **strictly above** the bar; no candidate's optimistic gain above the bar yields a hold; otherwise sampling continues (`src/core/flip_policy.h:70`, `:109`, `:152`).

Verification band `B` is at least twice the origin reading range divided by its midpoint and twice long-window sigma. A typed percentage supplies another floor; auto also takes the previous anchor band and twice maximum observed pair jitter/one-command quantum. Required gain is `min(1, B * margin)`. The chooser's model-space bar is `min(1, required_gain/kappa)`; `kappa` starts at one and learns delivered/predicted gain magnitude. Noise-only refusal keeps sampling to the cap instead of immediately treating the current split as optimum (`src/core/flipctl.cc:740`, `:759`, `:857`).

A candidate must also be verifiable and pay its predicted cost. Let `sigma` be the larger of origin relative standard deviation and long-window sigma, `n_o` origin readings, and `g` calibrated mean gain. Required target readings are

`n_t = ceil(1 / [(g/(4*sigma))^2 - 1/n_o])`, at least one.

A noiseless origin needs one; nonpositive denominator, fewer than two origin readings, nonpositive gain, or a result above the model reading cap means continue measuring origin, then hold at the cap. Predicted transfers are `clients * abs(io_after-io_before)/max(io_after,io_before)`, multiplied by the measured actual/naive transfer ratio. Measured transfer cost is total lost commands divided by clients moved; it is zero before the first measured move. The blackout is `(mean flip ticks + 3 + n_t - 1) * tick_seconds`. Flip duration has a one-tick floor even though its completion is polled eight times per tick (`src/core/flip_policy.h:325`, `:334`, `:392`, `src/core/flipctl.cc:831`).

The stationarity horizon starts at first non-idle boot evidence or the most recent automatic change trigger. Let `C` be predicted transfers times measured commands lost per client, `p=(misses+1)/(moves+2)`, `R0` the current origin reading, `T` stationarity seconds, and `Tb` blackout. The **implemented** cost test is:

`calibrated_gain_low * R0 * max(0,T-Tb) > margin * [C*(1+p) + p*R0*Tb]`.

The blackout risks the entire origin throughput. `gain_mean` is an unused argument of `flip_cost_gate`, despite the older header equation multiplying blackout by gain. A forced directed seek bypasses price, saturation, and projection acceptance but still passes through measurement and outcome handling (`src/core/flip_policy.h:476`, `src/core/flipctl.cc:831`).

### Testing the outcome and preventing repeated moves

After a completed role transaction, rate sampling resets. Target readings accumulate a mean, compared with the origin mean. At target reading `k`, the acceptance threshold is `max(verification band, 2*sigma*sqrt(1/n_o + 1/k))`. Delivered gain strictly above it is a hit; strictly below its negative is an immediate miss; otherwise reaching the planned target-reading count is a miss. A miss issues a return to that hypothesis's departure split. A refused return or unexpected split falls back to the highest individual recorded rate in the trail, not to a fitted throughput curve (`src/core/flip_policy.h:353`, `:385`, `src/core/flipctl.cc:955`, `:980`).

A hit records outcome and starts a fresh model window **at the landing**. Further steps must pass all gates, avoid previously recorded splits, and exceed the last step's demonstrated prediction error `max(0, previous predicted - previous delivered)`. A later miss returns to this landing, not necessarily to the maneuver's original split. Thus `Seeking` is neither an adjacent exhaustive sweep nor a single immutable jump. The trajectory can contain several accepted model-directed moves and a final return (`src/core/flipctl.cc:816`, `:928`).

The cost learner sums `max(0, rate_before * transition_seconds - commands_served)` over completed flips and counts actual transferred clients. Both outward and return flips contribute. Refusals do not. Outcomes increment moves/misses; positive predictions contribute to magnitude calibration and delivered gains are clamped to `[0,predicted]`, with misses contributing zero. `kappa = (sum_delivered + gbar)/(sum_predicted + gbar)`, clamped to `[0,1]`, where `gbar = sum_predicted/max(1,moves)`. The controller passes the already calibrated `hyp_predicted_` into this learner, although `record_outcome`'s comment says it expects the prediction before kappa (`src/core/flipctl.cc:653`, `:905`, `:999`, `src/core/flip_policy.h:419`).

Settling disarms maneuver-only age sampling before relearning the anchor. With fingerprinting enabled, it requires `max(1,nthreads)` monitor observations with at least one newly closed IO fingerprint window and a stabilized rate; maneuver-time mix anchoring uses `max(1,floor(log2(nthreads)))` such observations. Many IO windows consumed in one tick still advance this learning count by one. The anchored rate is the mean of collected settling readings, and its jitter includes their min/max range. A returned miss is voided only if correcting target gain for the newly measured origin baseline would change the verdict to a hit. Otherwise the model margin doubles when its old band product is below one; a delivered changed split halves margin toward one. The chooser separately clamps the required-gain product to one (`src/core/flipctl.cc:230`, `:297`, `:1016`, `:1185`).

For a mix/rate-triggered maneuver that ends at its starting split, the responsible trigger's required consecutive confirmations double, capped at `max(2,nthreads)`; a changed split halves them toward two. Thresholds are not raised beyond all possible normalized mix distances. Other anti-thrash mechanisms are sampled-window confirmation, judge-before-learning, movement-contamination resets, a same-split no-op guard, saturation/cost/confidence gates, refinement's visited/error checks, and measurement only after sampling disarm. There is no proof of an unchanged workload during a maneuver: automatic mid-maneuver change evidence is ignored (`src/core/flipctl.cc:613`, `:1041`, `:1124`).

### The role-change actuator

Manual and automatic requests use the same `Server::flip_begin`. IO+EX counts must conserve the existing physical-thread total and leave at least one of each, or at least one complete sibling pair of each under SMT mode. Fused mode, loading, snapshots, concurrent flip, invalid coordinator, and insufficient conversion candidates refuse. Same-split requests complete immediately with zero transfers. A new flip withdraws uncommitted continuous-LB `ExDrain`/`ClientDrain`; an already asynchronous `ClientMoving` is allowed to finish during IO drain. Refused targets remain visible in the report even when live counts differ (`src/core/server.h:1463`).

Conversion candidates are sorted by ascending sampled occupancy, descending physical thread ID on ties. Selection spreads conversions across L3 domains: choose a domain with fewest conversions taken, most remaining candidates on ties, then the first sorted candidate in that domain. Sibling pairs convert together. IO shrink excludes the coordinator, AOF writer, UNIX-listener owner, and their paired siblings. Growing IO selects from executors. Clients of other IOs and shards of surviving EXs can also move because the actuator repartitions the **entire** set with the count-constrained weighted partitioner; it does not merely evacuate converted threads (`src/core/server.h:1543`, `:868`, `:994`).

The control record has a 64-bit flip epoch and acknowledgements encoded `(epoch << 8) | uint8(stage)`. The coordinator publishes these stages and wakes peers; each physical loop acknowledges only its current epoch/stage. The five-second deadline applies before `ClientCommit`. After crossing that irreversible commit boundary, the controller must finish installation; timeout is not an automatic rollback (`src/core/server.h:1651`, `src/core/io_loop.h:3113`).

| Stage | Work required before advancing |
| --- | --- |
| `Planning` → `IoDrain` | Publish target and conversion plan; pause dispatch and freeze the set of admitted work. |
| `IoDrain` | Every current IO drains executor/ROB/output/transit work, including an outstanding LB client transfer. Coordinator computes the full client partition and verifies transfer-lane capacity. |
| `IoPrepare` | Current IOs reserve incoming state; EXs becoming IO prepare listeners and dormant IO resources on their own physical threads. |
| `ExDrain` | All current EXs reach the ownership safe point. Coordinator computes the final shard partition and reserves destination membership capacity. |
| `ClientPrepare` | Source IOs cancel receives and extract reversible catalog/routing state; converting IOs quiesce accepts. A busy client retries until the precommit deadline. |
| `ClientCommit` | Source IOs publish connection-owner edges and send the prepared transfer records. |
| `ClientInstall` | A second full IO/transit drain waits for transfer installation and pubsub/tracking/notification traffic. Coordinator transfers every changed shard directly to its final owner, then publishes role changes. |
| `RoleReady` | Physical threads leave their old loop and activate the other prebuilt loop. IOs rehome pubsub indexes, match client quotas, and wait for global pubsub transit count zero. |
| `ShardCommit` → `ExInstall` | `ShardCommit` is immediately passed through: shard transfers already happened. Final EXs remask existing task storage to the new IO/EX producer geometry and rebind keyless-notification pointers. |
| `Idle` | Audit live/ready roles, one-owner partition, floor/ceil shard/client counts, and exact planned transfer count; finish manual command's ROB reply. |

The stage implementation is `src/core/io_loop.h:3001`, with EX preparation/drain/install in `src/core/ex_loop.h:1816`, the actual early shard/role edges in `src/core/io_loop.h:2977`, and final conservation checks in `src/core/server.h:1718`. Precommit failure enters `Rollback`: wait for outstanding receive/accept cancellation, restore prepared clients/listeners, cancel future IO listeners, collect both roles' acknowledgements, and return an error while preserving the requested target. Role changes never publish an intermediate `Idle` role; `Idle` in a conversion-plan slot means “this thread is not converting.”

## 8. Overlap and reordering change different parts of the schedule

### Overlap is a fixed loop schedule, not another thread stage

`--overlap` is boot-selected, with alias `--thread-pipeline`. Legacy `--genthread-schedule coarse|iofused|streams` lowers to 0/1/2; `streams` now selects the new whole-batch three-way schedule. Split accepts 0/1 and rejects 2. Fused overlap 1/2 requires io_uring. Read-local is active only in fused overlap 0. All supported schedules retain IO ownership of reply retirement and sends (`src/core/config.h:695`, `:1208`, `src/core/server.h:582`).

| Machine | Schedule in the work portion of a rotation | What independent work separates a load from use |
| --- | --- | --- |
| Split, overlap 0 | Ordinary receive/parse/dispatch, completion collection, ordered serve/send; EX runs separately. | Each EX batch prefetches store slots before executing its tasks. |
| Split, overlap 1, shallow | Observe WB → receive/select clients → prefetch WB → parse/hash/quiet-post → retire/prepare WB → notify EX → submit/reclaim WB. | Parsing runs between remote reply-state/payload hints and retirement. |
| Split, overlap 1, deep | Receive → collect completions → parse/hash/post → gather WB → serve/submit. | Returns to natural order when enough parse work already supplies independent progress. |
| Fused, overlap 0 | Receive/parse → bounded EX batches/local-read work → WB. | Store prefetch is within EX batches; optional read-local has its own chunk prefetch/copy schedule. |
| Fused, overlap 1 | Observe/prefetch WB → targeted ordinary IFID → WB retirement/send preparation → coarse EX. | IFID fills the WB dependency gap. EX completion normally waits until the next rotation's WB selection. |
| Fused, overlap 2, gate closed | IFID → coarse EX → WB. | No extra WB/EX interleave. |
| Fused, overlap 2, gate open | Freeze/prefetch WB → IFID → first EX batch's store prefetch → frozen WB retirement/send preparation → EX execution; later EX batches run normally. | WB fills the first EX prefetch gap as well as IFID filling the WB gap. |

The split schedules are implemented at `src/core/io_loop.h:6589`; fused overlap 1 at `:5835`, overlap 2 at `:5967`, and the first-EX-batch callback at `src/core/ex_loop.h:2120`. IFID “post” in the split pipeline sends notifications after the parser's quiet task publications; it does not hold every parsed task unpublished until that stage.

Split overlap 1 caps a selected IFID batch at 64 clients and parsing at 64 operations per client, with 64 WB clients. It prefetches at most all 64 possible ROB slots and the first 512 bytes of each ready borrowed payload, one hint per 64-byte line. Its four-completed-pass gate enters natural order at sum >=256 parsed frames and leaves at sum <=128. Every 64 rotations IFID nominates visited clients as a mask-independent WB backstop. Each pass clears its synchronous IFID/WB buffers; no residual operation context survives the rotation (`src/core/iopipe_pipeline.h:15`, `:39`, `src/core/io_loop.h:6283`, `:6589`).

Coarse fused geometry is 32 parse operations, 32 EX tasks per batch, 16 WB connections. The overlap family uses constants of 128 parse/EX operations and 64 WB connections; the currently reachable iofused IFID path invokes ordinary uncapped coarse dispatch, so the parse constant does not bound the entire rotation. EX can drain several whole batches in one pass. The overlap-2 gate starts closed and uses the **maximum work observed across the completed IFID/EX pass or WB batch**, opening the next rotation at >=8 and closing it below 8. The EX/IFID observation is an operation-counter delta for the pass, not strictly one batch's occupancy (`src/core/genthread_pipeline.h:11`, `src/core/io_loop.h:5605`, `:5967`).

The open gate's WB batch and first EX batch both finish synchronously. AOF send eligibility is captured before EX execution; exceptional retry/snapshot/LB debt consumes the WB callback before running that debt so the captured gate cannot retire newly completed unsafe work. The loop has one completion harvest and one outer network submission policy: SEND-bearing batches submit immediately, non-SEND work may coalesce for four rotations, and idle forces the sweep/park path. Full SQ submission resets the coalescing count (`src/core/ex_loop.h:475`, `src/core/io_loop.h:871`, `:912`).

These schedules buy countable load-to-use distance, fewer repeated client/completion walks, and coalesced notifications/submissions. They also change batch size, which operations become reply-eligible in the current rotation, and how long control SQEs wait. These are scheduling costs, not measured rate results from this review. The substantial old A/D executor-context and unpublished IFID “streams” implementation remains below the dispatch branches but is unreachable from the accepted overlap values (`src/core/io_loop.h:528`, `src/core/genthread_pipeline.h:36`).

### Reordering is an optional executor batch permutation

`--ex-sched 1`, default 0, applies before store prefetch. It walks contiguous eligible runs and cannot cross a task with scatter/tagged EXEC state, no client, blocking state, or admin/connection/global/cursor/random/config/script/pubsub/transaction/stream/subcommand/flip flags. A same-shard MGET/MSET that took the local shortcut can participate. There is no persistent scheduler queue or cross-batch choice (`src/core/ex_loop.h:2154`, `:2310`, `:2763`).

Each task's primary rank is `op_id - client.rob.flush_id`, limited to 0–63. Head reads are sampled newest-to-oldest so concurrent prefix retirement cannot give an older same-connection task a larger rank than its successor. The secondary key is boot-stamped `CommandLengthClass` (Point, SmallMulti, Long), not a measured duration or argument-size estimate. `atomic_hazard` widens to Long. For each connection, effective class becomes the prefix maximum; an unrepresented earlier rank or gap in IDs widens to Long. A nonincreasing per-connection op ID aborts the permutation and retains FIFO (`src/core/ex_loop.h:2196`, `:2225`, `src/cmd/commands.cc:82`).

Stable counting distribution uses **192 buckets = 64 ranks * 3 classes**, two 192-byte count/cursor arrays, a three-word occupied mask, and a scratch task array. Single-client runs, homogeneous classes at adjacent ranks, and already sorted keys avoid the permutation. A changed order copies every selected 32-byte Task into scratch and back. This prioritizes tasks nearer an immediately emit-able reply and then shorter static classes, while preserving each represented connection's order. It does not impose cross-client ordering; the ROB still preserves each connection's output (`src/core/ex_loop.h:2182`, `:2261`).

**The supported selector combination exceeds the scheduler's storage.** `kExecBatch` is fixed at 32 and asserted <=32, so `base_lengths`, schedule keys, and output tasks hold 32 entries; the per-connection hash scratch holds 64 slots with one 64-bit occupancy mask. Fused overlap 1/2 calls this same scheduler with a task count up to **128**, with no bound check or config rejection. A run larger than 32 writes outside `base_lengths` even before the one-client early exit in the deeper helper. `--thread-mode 1s --overlap 1|2 --ex-sched 1` therefore has a reachable stack-overwrite path; the source cannot be described as supporting arbitrary composition of these independent-looking knobs (`src/core/ex_loop.h:46`, `:404`, `:2131`, `:2190`, `:2302`, `:2311`, `src/core/config.h:1208`).

## 9. Selectors that change the machine

The following switches change an ownership boundary, a consistency protocol, a scheduling algorithm, or the lifetime of request data. Their defaults describe the source defaults, not the maintainer's gate geometry.

| Selector and source default | Concrete change |
|---|---|
| `--thread-mode 2s` versus `1s` | Separate IO/EX role loops and cross-role task handoffs versus one loop scheduling both duties. Fused rejects `--ratio` and automatic flip. Both still have owner-only writes and cross-thread task lanes (`src/core/config.h:318`, `:684`, `:1222`). |
| `--ratio`, `--place`, `--shard-home`; `--smt-mode 0` versus `1` | The first three choose physical role and shard ownership maps. SMT 1 changes the role-conversion unit from a logical CPU to a complete sibling pair and rejects incomplete or split-role pairs; it does not double any queue or ROB width. ## DIVERGENCES

Ranked by how seriously the mistaken model changes the safety or behavior a reader would infer. These are comparisons with executable paths, source comments/names, and the supplied correctness laws. No repository design documents were consulted. The defect paths below are established by source inspection; they were not exercised on the machine.

1. **Shard quiescence does not close every owner-private lifetime.** The mover correctly rebinds read-local retirement/cache sinks before publishing routes, but leaves `AtomicEntry::owner_refs` pointing into the original owner's plain counter. Records of one group split across old/new owners can concurrently decrement that counter after migration. Admission/apply counts reaching zero does not prove those records are gone. This contradicts the required all-structures-in-one-critical-section ownership law and can corrupt the group lifetime accounting (§5; `src/core/ex_loop.h:1794`, `src/core/server.h:2040`, `src/store/flatstore_atomic.inc:1572`).

2. **EXEC does not give all its reads a consistent transaction view.** Cut admission recognizes individual cross-shard read commands, not the transaction's combined read set. More decisively, `execute_local_command` ignores even a registered cut and always uses `UINT64_MAX`. Separate `GET a; GET b` children can read opposite sides of a foreign atomic commit and return a torn pair. A single commit decision for the transaction's writes is therefore not evidence that EXEC's result is isolated or that every read observes atomic foreign groups (§2; `src/cmd/multi.inc:664`, `:1055`, `:1078`).

3. **Script certification does not exclude a plain writer after validation.** The comments say concurrent plain writers are caught by read-set validation and that the reserved ticket orders later writers after the script. Validate is followed by a separate Unpin wave and then Apply. A plain `INCR` between Unpin and Apply can execute without any record/ticket, and Apply does not validate again: the script and plain command can both increment zero to one and both succeed. Global certification excludes other scripts only. The exact two-increment execution is in §2 (`src/cmd/scatter_engine.inc:3510`, `:3569`, `src/cmd/atomics_glue.inc:966`).

4. **WATCH's nonblocking conflict rule does not cover competing EXEC validation claims.** Two transactions watching the same keys on different owners can acquire blocking reservations in opposite orders and both wait forever at the all-owner WATCH barrier. `watch_validate_and_reserve` returns on the other transaction's blocking claim before reaching its dirty-and-abort rule for nonblocking atomic writers. Even two read-only EXECs can enter the cycle described in §2; the retry queues supply no tie-break or timeout (`src/cmd/multi.inc:1203`, `:2176`, `:2261`, `src/core/ex_loop.h:3025`).

5. **An armed local-read lane uses the forbidden reader-validation/retry mechanism.** It checks a mutation generation around table loads, probes and copies; both MGET paths retry the complete window up to twice. GET without capture retries up to three times. This is present in the ordinary build when the lane is enabled, even though immutable replacement handles normal SET lifetime. Accepted build variants additionally perform sequence-protected in-place overwrite. “No reader retries and no seqlocks on the per-operation path” is not an accurate description of this implementation (§3; `src/store/flatstore.h:914`, `src/core/ex_loop.h:1170`, `:1299`, `:1450`, `src/store/read_local_settax.h:17`).

6. **Accepted scheduling knobs can overrun executor stack scratch.** Fused overlap 1/2 drains batches of up to 128 tasks into the same optional scheduler whose arrays are sized by `kExecBatch=32`. No validation rejects the combination. `base_lengths[32]` is already out of bounds before the scheduler can take its one-client shortcut. Independent-looking flags therefore do not compose into a supported machine (§8; `src/core/ex_loop.h:404`, `:2311`, `src/core/config.h:1208`).

7. **Ownerless WATCH cleanup is only partly treated as ownerless.** Disconnect cleanup deliberately posts a tagged MULTI task with `client=nullptr`. The dispatch-order branch explicitly guards it, but the immediately following maxmemory/no-touch branch unconditionally reads `t.client->rob()`. Closing a WATCH-bearing connection with maxmemory enabled reaches a null dereference before the cleanup handler. The explanatory comment correctly says this task has no ROB; the next branch violates it (`src/cmd/multi.inc:1749`, `:1776`, `:2105`, `src/core/ex_loop.h:2784`, `:2826`).

8. **The continuous mover repairs the notification pointer after execution resumes.** Its comment describes a repaired owner binding, but `lb_control_pass` performs that rebind at the end of the first resumed pass. Earlier work in that pass can publish into the old executor's plain `notify_keyless_pending_`. The forced sweep addresses eventual output; it does not establish ownership or synchronization for the flag. Flip's explicit ExInstall is a stronger boundary (§5; `src/core/ex_loop.h:755`, `:1833`, `:1854`, `src/core/shard.h:165`).

9. **Fingerprint “publication” is not a C++ synchronization protocol.** `published_.closed_windows` is an ordinary integer written last; the monitor first copies the entire ordinary struct and then tests its copied counter. Neither operation synchronizes concurrent accesses, and no lock spans the writer. The controller also reads plain `total_commands_` concurrently with owner increments. These are data races, not merely approximate-but-coherent statistical snapshots. The writer comment's “checks this field before consuming” does not describe the copy in `sample_fingerprint` (§7; `src/core/flipctl.h:117`, `src/core/flipctl.cc:297`, `src/core/thread.h:425`).

10. **The “exact per-key” filter is a lossy hash-cell filter, and its epoch-wrap proof is incomplete.** A 4,096-cell table with 32-bit fingerprints admits false positives and sticky wildcard cells, so unrelated keys can be refused. Its 32-bit epochs wrap by addition; unlike the shard generation, they do not poison at exhaustion. The comment rules out wrap using a bounded owner rate, but the code places no wall-clock bound on a preempted reader's copy window. A full `2^32`-transition wrap can compare equal. Rate alone does not prove absence of that ABA (§3; `src/core/config.h:251`, `src/store/foreign_read_safety.h:195`, `:224`).

11. **Several advertised zero/off states retain or enable machinery.** `atomic 0` is called “fully off: no allocation” but EXEC/scripts force it and multi-shard reads allocate/register cuts even in an idle atomic gap; disabling it cannot discard retained records/pools. `zc-min 0` disables GET borrowing but makes every nonempty non-integer scattered MGET value borrowed. `script-crossshard-conflict-retries 0` keeps the facility and disallows retries, contrary to the four knobs' shared zero-disables comment. `lb-age-sample-rate 0` can be armed by flip; `flip-auto-band 0` keeps the boot maneuver and allocations. Separately, the documented unlimited-zero knobs conflict with the supplied project-wide zero-means-off convention (§9; `src/core/config.h:264`, `:337`, `:352`, `:370`, `src/cmd/scatter_engine.inc:1818`, `:2874`, `:3516`).

12. **The local shortcut and read-cut comments conflate shards with owners.** `same_owner` compares shard IDs, and `read_fanout` counts shard groups. Two shards on one physical executor still get multiple tasks and a cut. The comment that a single-owner scatter resolves in one task is false. Owner-batched publication/completion changes tail/RMW counts without implementing the deleted executor-major task collapse (§4; `src/cmd/scatter_engine.inc:1742`, `:1798`, `:1812`).

13. **Cleanup budgets do not bound cleanup work within a shard.** Any positive `atomic_sweep` budget allows the whole eligible prefix to collapse. The inversion test can compare entry pairs and key spans; conflicting cases allocate a temporary hash table and sort retirements. The executor's 64/256 numbers cannot be used as an upper bound on operations, keys, allocations, or time in one cleanup pass (§2; `src/store/flatstore_atomic.inc:683`, `:1510`, `:1703`, `src/core/ex_loop.h:2022`).

14. **ROB handles and its “universal quiescence fence” have weaker meanings than the comments give them.** `at(id)` masks into recycled slots without checking the ID's generation; handles are safe because tasks must not outlive retirement. Chunk pointers are plain `Op*`, with publication ordered by the surrounding task handoff, not atomic chunk-pointer release/acquire. `dispatch==flush` does not release kernel receive/send buffers, borrowed output, TLS state, pipeline references, or WATCH cleanup. Teardown/migration checks many additional fields despite the header claiming “exactly this and nothing else” (§4–5; `src/net/rob.h:14`, `:20`, `:759`, `:776`, `src/net/conn.h:713`, `src/core/thread.h:75`).

15. **Flip's statistical and time labels overstate what is observed.** Accepted two-tick means reuse their second tick; they are overlapping readings. A cap derived from 30 seconds bounds accepted reading count, not elapsed maneuver time. `T_stat` advances until an automatic trigger, but automatic change detection is ignored during maneuvers; elapsed stationarity is not proof that the workload remained unchanged. The header's “sampling costs no throughput” is a rate assertion, not a zero-work property: sampling executes per-frame counter stores on selected passes and arms task timestamps during maneuvers. Those operations are countable; their rate effect requires measurement (§7; `src/core/flipctl.cc:334`, `:504`, `:1108`, `src/core/flip_policy.h:13`).

16. **The implemented price and learning units differ from the policy header.** The header prices blackout as `P_miss * kappa * g_mean * R0 * T_black`; the function uses `P_miss * R0 * T_black` and ignores `gain_mean`. `record_outcome` asks for a pre-kappa prediction, while the controller gives it calibrated `hyp_predicted_`. The formulas in §7 describe the implementation; the header equation describes a different acceptance gate (`src/core/flip_policy.h:45`, `:419`, `:476`, `src/core/flipctl.cc:905`, `:999`).

17. **Load-balancing names hide different units and invariants.** The continuous move chooser uses item count as a tie-breaker rather than enforcing the full partitioner's floor/ceil constraint. Client planning moves one client even if `lb_move_cap` is larger. Counters named `bucket_moves` increment per shard. `home_domain_` changes on ownership reassignment without moving memory, so `foreign_ops` is not a measurement of cache/page locality (§5–6; `src/core/weighted_lb.h:131`, `src/core/server.h:1264`, `:1362`, `src/core/shard.h:379`).

18. **Fingerprint field/function names do not denote the quantities they suggest.** `value_bytes` includes every non-key argument, not just values; `AtomicGrouped` follows the boot configuration and command flags, not actual admission or live CONFIG state. The function described as “whole-signature distance including pass_depth” returns only half-L1 pass-depth distance. These change how INFO/controller traces should be interpreted (§7; `src/core/io_loop.h:5330`, `src/core/flipctl.h:158`, `src/core/flipctl.cc:89`).

19. **Abandoned scheduling descriptions remain adjacent to live code.** `io_loop.h` still says that only the send syscall moves between modes and advertises five loop shapes. In accepted modes, IO owns both retirement and sending; fused changes execution scheduling as well. The old streams A/D-context code remains unreachable beneath early returns for 0/1/2, while the `streams` alias selects the current three-way overlap schedule. `ShardCommit` is published after shard pointers/routes have already moved during ClientInstall. These names do not identify additional supported stages or commit edges (§7–8; `src/core/io_loop.h:10`, `:62`, `:528`, `src/core/config.h:702`).

## WHAT SURPRISED ME

- **There are at least four distinct clocks/lifetimes behind “epoch.”** A ticket is drawn before its decision is readable; the safe commit watermark can lag; a snapshot cut pins predecessor representation; a separate QSBR epoch pins foreign pointers. Admission lasts through reply retirement, while apply closes at decision. A single counter cannot replace any of these without changing who may reclaim or freeze what (`src/core/server.h:2560`, `:2772`, `src/core/read_local.h:378`).

- **The version header does not point to its own candidate.** It owns the displaced predecessor, and the next matching record carries its value after another replacement. Abort and out-of-order ticket repair therefore change how that physical-exchange history is interpreted, rather than undoing each write immediately (`src/store/flatstore_atomic.inc:1005`, `:1703`).

- **A command can release its read cut before it can release its reply.** Completion of the last future dereference lets IO remove the cut even when an older ROB slot prevents output. A borrowed MGET value then stays alive under a different owner-return protocol. An arena can survive both events because a committed record still points at its decision (`src/cmd/atomics_glue.inc:401`, `src/cmd/scatter_engine.inc:3997`).

- **Fusion retains a task mesh and an executor object with its own control ring.** It does not turn the general path into direct calls on whichever connection thread parsed the command. Both split roles are provisioned ahead of a flip, and task storage scales as `nthreads² * 1024 * 32` bytes across consumers before counting the other channel families. An individual producer can exhaust its assigned lane while most of that mesh is empty (`src/core/genthread.cc:88`, `src/exec/masked_queue.h:102`, `src/core/ex_loop.h:181`).

- **Cross-shard scripts run the command twice at the representation level.** Owners serialize the original data; one thread loads a private shard and runs Lua; owners then load the resulting write images into real stores. A server-wide certification flag covers even disjoint writing scripts, and its reserved ticket keeps the readable commit watermark behind while certification/apply is outstanding (`src/cmd/scatter_engine.inc:2381`, `:2443`, `:2474`, `:3536`).

- **MGET has a substantial fixed per-key result footprint.** Every gathered key gets 1,024 inline bytes even if its result becomes nil or a borrowed pointer. Borrowing starts above 1,024 bytes at the default GET threshold of 16,384, so GET and MGET with the same value size can have different allocation lifetimes and return-channel traffic (`src/cmd/scatter_engine.inc:56`, `:2874`).

- **The read-local lane shifts bounded-memory pressure to writers.** Its retirement FIFO allocates no overflow nodes; when 4,096 slots are occupied, the writer waits for a grace period inside the reclaim call. A reader can complete without a writer lock while still extending the lifetime of enough objects to stop that owner's executor and, in fused mode, its networking loop (`src/core/read_local.h:299`, `:416`).

- **Default periodic SAVE selects mutation observation without a subscriber.** Empty notification flags do not imply an unobserved write path. SAVE and tracking use the same handler-selection mechanism, and maxmemory can turn a nominal one-key write into an unenumerable foreign-read hazard through eviction (`src/core/ex_loop.h:1892`, `src/core/io_loop.h:7121`).

- **Several remnants are live allocations or accepted selectors, not just comments.** Every EX still contains a `WbEngine` used for reporting rather than sending; overwrite-study build variants remain selectable; the old streams code remains compiled source beneath unreachable dispatch arms. The active two-mode model must be reconstructed from branches and call sites, not from the surrounding historical vocabulary (`src/core/ex_loop.h:3330`, `src/store/read_local_settax.h:17`, `src/core/io_loop.h:528`).
